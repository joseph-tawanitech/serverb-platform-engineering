# B20.7 — Governed Security Actions

## Status

PASS — Governed Security Action Contract and Policy Integration

## Purpose

B20.7 establishes the control boundary between an AI security recommendation
and any future security action execution.

The AI Security Operator may recommend an action, but it does not receive
execution authority.

B20.7 converts the recommendation into a typed SecurityActionRequest and
evaluates it through the existing B20.2 operational security policy engine.

## Responsibilities

B20.7:

- defines the governed security action contract
- preserves the AI recommendation as action metadata
- identifies the requested operation, environment, asset and requester
- reuses the existing B20.2 policy engine
- returns ALLOW, REVIEW or BLOCK
- preserves policy ID and policy version
- identifies whether authorization is required before execution

B20.7 does not:

- execute shell commands
- execute SSH operations
- execute Kubernetes changes
- execute Ansible
- execute EDA workflows
- directly modify infrastructure
- grant AI execution authority
- replace the B20.2 policy engine

## Policy and Authority Separation

A policy ALLOW means that the requested operation is permitted by the
configured security policy.

It does not mean that infrastructure execution has already been authorized
or performed.

TAP authority remains responsible for the authorization boundary before an
action reaches a future execution mechanism.

A REVIEW result requires review or authority before execution.

A BLOCK result prevents the proposed action from proceeding through the
governed action path.

## Reuse

B20.7 deliberately reuses:

- B20.2 SecurityPolicy
- B20.2 SecurityRequest
- B20.2 PolicyDecision
- B20.2 evaluate_policy()
- B20 security decision and risk contracts

No second policy engine is introduced.

## Future Execution

B20.7 intentionally does not implement an execution engine.

Future governed execution may dispatch to an approved execution mechanism,
including infrastructure-specific paths such as Kubernetes remediation or
an EDA -> Ansible workflow.

Those execution mechanisms must remain behind the TAP authority boundary.
