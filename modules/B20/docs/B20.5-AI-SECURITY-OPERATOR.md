# B20.5 — AI Security Operator

## Purpose

The **AI Security Operator** is the intelligence layer of TAP B20. Its role is to investigate security conditions, interpret evidence, identify potential risks, correlate related observations, and produce security findings and recommendations.

The AI Security Operator does not replace monitoring systems, security evidence collection, RAG, MCP, or TAP governance. Instead, it brings these capabilities together so that AI can reason over authorized security information.

The operator consumes normalized security evidence from the B20 Security Evidence Layer. It can use current authorized information exposed through MCP together with relevant historical and technical knowledge retrieved through the existing B19 RAG capability. This allows the operator to examine both **what is happening now** and **what relevant knowledge or history may explain it**.

For example, an unusual authentication event, Kubernetes workload change, firewall observation, system configuration finding, or infrastructure security alert can be correlated with previous incidents, policies, runbooks, and technical documentation.

## Provider-Neutral AI

The AI Security Operator is **provider-neutral**. It communicates through the TAP AI Gateway rather than depending directly on a specific AI model.

This allows approved models such as Claude, GPT, Grok, Qwen, or future providers to be added, replaced, or routed according to TAP configuration without redesigning the B20 security architecture.

## TAP Authority Boundary

The AI Security Operator is **not the security authority**.

AI may investigate, reason, identify risks, and recommend or propose an action. TAP remains responsible for policy evaluation, authorization, execution control, verification, and recording.

The governed security lifecycle is:

**Evidence → AI Investigation → Finding/Recommendation → TAP Policy → Authorization → Governed Action → Verification → Audit**

This separation allows AI to provide security intelligence while keeping operational authority under deterministic TAP controls.

### Live Model Runtime Validation

Full live B20.5 investigation execution was attempted through the existing TAP AI Gateway:

B20.5 → B15 AI Gateway → Model Router → Ollama → Qwen3:4b

The complete B20.5 investigation prompt was approximately 21,506 characters.

The original B15 Gateway message-content limit was 12,000 characters. This prevented the complete reusable B17 investigation prompt from reaching the model. The Gateway contract was therefore deliberately increased to 32,000 characters.

After this controlled Gateway change, the B20.5 request passed Gateway input validation and proceeded to the Ollama/Qwen runtime.

The active local Ollama inference process was observed with:

    -c 4096

This indicates that the current Qwen runtime is operating with a 4096-token context configuration.

The full B20.5 investigation request did not complete within the 150-second client timeout. The B20.5 Gateway adapter consequently reported:

    TimeoutError: timed out

B15 remained operational during the test. Its health endpoint returned HTTP 200, while the investigation request subsequently resulted in:

    POST /v1/chat → 502 Bad Gateway

This establishes the following sequence:

    B20.5
        ↓
    B17 prompt construction
        ↓
    B15 Gateway
        ↓
    Ollama
        ↓
    Qwen3:4b
        ↓
    inference did not complete within current runtime conditions
        ↓
    client timeout
        ↓
    B15 upstream failure / HTTP 502

### Root Cause Classification

The immediate failure was an inference timeout in the local AI runtime.

The identified environmental constraint is the current Ollama/Qwen runtime configuration, including its 4096-token context configuration and the available local compute/runtime capacity for processing the complete B20.5 investigation workload.

The evidence does not establish that the 4096-token setting alone is the sole cause of the timeout. Other runtime factors such as CPU, memory, model performance, context processing overhead, and inference speed may contribute.

Therefore the issue is classified as:

**Environment / AI Runtime Capacity Limitation — Deferred**

It is not classified as a B20.5 architectural failure.

### Deferred Resolution

The local Qwen/Ollama runtime will not be repeatedly modified during the current B20 implementation cycle.

The limitation is recorded for later infrastructure optimization and Server B migration.

Future resolution may include:

- increasing the Ollama/Qwen context configuration;
- evaluating the memory and CPU requirements of a larger context;
- using a larger or more capable Qwen model;
- adding GPU resources where appropriate;
- tuning inference/runtime parameters;
- using an approved cloud AI provider through the existing B15 Gateway;
- testing the same B20.5 investigation contract across multiple approved models;
- establishing production model-routing and fallback policies.

The B20.5 architecture and B17 investigation contract should not be weakened or redesigned merely to accommodate the current temporary Qwen3:4b development runtime.
