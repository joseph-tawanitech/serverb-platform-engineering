# 1. Objective

B18.7 introduces the Evidence Sufficiency layer for the TAP incident investigation pipeline.

The purpose of this layer is to determine whether the evidence currently available is sufficient to support continued investigation of a hypothesis.

Evidence sufficiency is deliberately separated from root cause analysis.

B18.7 does not declare the root cause.

It determines whether the available evidence is:

* insufficient
* partial
* sufficient

This creates a controlled gate between hypothesis generation and root cause analysis.

---

---

# 3. Core Principle

The B18 investigation architecture follows:

> Evidence first. Explanation second. Authority last.

And:

> Observation is not explanation.

> Correlation is not causation.

> Hypothesis is not root cause.

> Recommendation is not execution.

B18.7 exists to prevent weak or incomplete evidence from being treated as sufficient support for a root-cause conclusion.

---

# 4. What Is Evidence Sufficiency?

Evidence sufficiency means determining whether there is enough relevant and reasonably reliable evidence to continue toward a stronger investigation conclusion.

Examples:

```text
Two independent reliable evidence items
        ↓
Potentially sufficient
```

```text
One weak evidence item
        ↓
Insufficient
```

```text
Strong evidence exists
but another required source is missing
        ↓
Partial
```

Sufficiency is therefore an evidence assessment, not a causal conclusion.

---

# 5. Sufficiency Status

B18.7 defines three statuses:

```text
INSUFFICIENT
PARTIAL
SUFFICIENT
```

Conceptually:

```text
INSUFFICIENT
    ↓
PARTIAL
    ↓
SUFFICIENT
```

The actual investigation may move between states as additional evidence is collected.

Example:

```text

```

B18.7 evaluates the evidence available for this hypothesis and records the result.

The hypothesis itself is not converted automatically into a root-cause statement.

---

# 8. Reliable Evidence

The evaluator treats these reliability levels as reliable supporting evidence:

```text
MEDIUM
HIGH
```

The following are not counted as reliable supporting evidence:

```text
UNKNOWN
LOW
```

This allows the sufficiency decision to consider evidence quality rather than evidence quantity alone.

---

# 9. Deterministic Sufficiency Rules

The current evaluator uses explicit deterministic rules.

## Rule 1 — No supporting evidence

If the hypothesis has no available supporting evidence:

```text
INSUFFICIENT
```

Reason:

```text
There is not enough supporting evidence.
```

---

## Rule 2 — No reliable supporting evidence

If supporting evidence exists but none has MEDIUM or HIGH reliability:

```text
INSUFFICIENT
```

The presence of evidence alone is not treated as sufficient.

---

## Rule 3 — Missing referenced evidence

If the hypothesis references an evidence ID that is not available:

```text
PARTIAL
```

The missing evidence ID is recorded in metadata.

---

## Rule 4 — Contradicting evidence

If contradicting evidence is present:

```text
PARTIAL
```

The contradiction remains visible and prevents the evidence set from being automatically considered sufficient.

---

## Rule 5 — Missing required sources

The evaluator can receive a list of required evidence sources.

Example:

```text
Required:
- logs
- prometheus
- traces
```

If one or more required sources are not represented:

```text
PARTIAL
```

Missing sources are explicitly recorded.

---

## Rule 6 — Two reliable supporting items

When:

* at least two supporting evidence items exist
* at least two supporting items have MEDIUM or HIGH reliability
* no contradicting evidence exists
* no referenced evidence is missing
* no required source is missing

the result is:

```text
SUFFICIENT
```

The current deterministic confidence value is:

```text
0.9
```

This value represents the confidence of the sufficiency assessment, not certainty that the hypothesis is the root cause.

---

## Rule 7 — One reliable supporting item

When only one reliable supporting item exists:

```text
PARTIAL
```

The current deterministic confidence value is:

```text
0.5
```

Additional evidence may be required before proceeding to a stronger RCA conclusion.

---

# 10. Confidence Meaning

The confidence field in B18.7 refers to the confidence of the evidence-sufficiency assessment.

It does not mean:

```text
"90% certain this is the root cause"
```

For example:

```text
0.9
```

means the evaluator classified the evidence set as sufficiently complete according to its current deterministic rules.

Root-cause confidence belongs to the later RCA stage.

---

# 11. Missing Evidence

The evaluator records evidence referenced by a hypothesis that is not currently available.

Example:

```text
Hypothesis:
E-001
E-002
E-999

Available:
E-001
E-002

Missing:
E-999
```

The result is:

```text
PARTIAL
```

This preserves traceability and prevents the missing evidence from disappearing silently.

---

# 12. Missing Sources

The evaluator supports required-source checks.

Example:

```text
Required Sources:
- Kubernetes
- Prometheus
- Logs

Available:
- Kubernetes
- Logs

Missing:
- Prometheus
```

The result becomes:

```text
PARTIAL
```

This supports multi-source incident investigation and makes source gaps visible.

---

# 13. Contradicting Evidence

Contradicting evidence is explicitly counted.

Example:

```text
Supporting:
E-001
E-002

Contradicting:
E-003
```

The result is:

```text
PARTIAL
```

This prevents the investigation from treating supporting evidence as the only relevant evidence.

Contradicting evidence remains available for later hypothesis testing and RCA.

---

# 14. Evidence Traceability

Every evidence reference is preserved.

Example:

```text
Hypothesis
    ↓
Evidence IDs
    ↓
Sufficiency Assessment
    ↓
Reasoning
    ↓
Metadata
```

This allows an investigator to determine why a sufficiency decision was produced.

---

# 15. Reasoning

The evaluator generates an explicit reasoning summary.

Examples include:

```text
Evidence is insufficient because there is not enough
reliable supporting evidence for the hypothesis.
```

or:

```text
Evidence is sufficient because at least two supporting
evidence items are available, at least two are reliable,
and no contradictions or required-source gaps were identified.
```

The reasoning is deterministic and explainable.

---

# 16. Evidence Source Normalization

Required evidence sources are normalized before comparison.

For example:

```text
Logs
logs
LOGS
```

are treated as the same source identifier.

This prevents simple capitalization differences from producing false missing-source conditions.

# 19. Relationship to B18.8 Root Cause Analysis

B18.8 will use the results of B18.7 to perform Root Cause Analysis.

Conceptually:

```text
Hypothesis
    ↓
Evidence Sufficiency
    ↓
Sufficient / Partial / Insufficient
    ↓
Root Cause Analysis
```

A sufficient evidence assessment does not automatically mean the hypothesis is the root cause.

It means the available evidence meets the current sufficiency criteria for moving into the next investigation stage.

# 21. Security and Authority Boundary

B18.7 is an investigation assessment component.

It does not:

* execute shell commands
* modify Kubernetes resources
* modify files
* restart services
* run Ansible
* run Terraform
* modify firewall rules
* authorize remediation
* execute remediation

It produces assessment data only.

TAP remains the authority boundary for authorization and execution.

# 22. Deterministic Design

The initial B18.7 implementation is deterministic.

This provides:

* reproducibility
* predictable outcomes
* transparent rules
* testability
* auditability
* controlled AI integration later

AI may later help interpret complex evidence, but AI output must still pass through evidence validation and TAP governance.

# 24. Current Limitations

The current implementation deliberately does not:

* determine causality
* identify the root cause
* calculate causal probability
* rank competing root causes
* automatically request missing evidence
* perform active evidence collection
* use AI reasoning
* authorize remediation
* execute remediation
* verify remediation

These functions belong to later B18/TAP layers.

# 28. Investigation Vocabulary

The distinction between these concepts is essential:

```text
Evidence
    = What was observed

Observation
    = A recorded fact or condition

Symptom
    = An observable indication of a problem

Timeline
    = When observations occurred

Correlation
    = Which observations are related

Hypothesis
    = A possible explanation

Evidence Sufficiency
    = Whether enough evidence is available

Root Cause
    = The explanation sufficiently supported by investigation

RCA
    = The process of establishing the supported explanation

Recommendation
    = A proposed action

Authorization
    = Permission for an action

Execution
    = Performing an authorized action

Verification
    = Determining whether the action achieved the expected result

Audit Trail
    = The recorded history of investigation and operational decisions
```

Core principle:

> Observation is not explanation. Correlation is not causation. Hypothesis is not root cause. Recommendation is not execution.
