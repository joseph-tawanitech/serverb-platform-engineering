# 1. Objective

B18.6 introduces the Hypothesis Generation layer for the TAP incident investigation pipeline.

The purpose of this layer is to transform correlated incident evidence into structured possible explanations that can be investigated further.

A hypothesis is not treated as a confirmed root cause.

B18.6 therefore establishes an explicit separation between:

* observed evidence
* correlated evidence
* possible explanations
* evidence-supported root cause

The initial implementation is deterministic so that its behavior is explainable, testable, and reproducible.

---

B18.6 operates after correlation and before evidence sufficiency and root cause analysis.

---

# 3. Core Principle

B18 follows the principle:

> Observation is not explanation.

More specifically:

> Correlation is not causation.

> Hypothesis is not root cause.

> Recommendation is not execution.

B18.6 creates possible explanations but does not authorize, execute, or verify remediation.

---

# 4. What Is a Hypothesis?

A hypothesis is a proposed explanation that may account for one or more observed conditions.

Example:

```text
Evidence:
- Pod restarted
- Application reported database connection errors
- Same workload was affected

Correlation:
- Evidence occurred within the same incident context
- Evidence references the same resource

Hypothesis:
- A database connectivity condition may have contributed
  to the application failure and pod restart
```

The hypothesis remains subject to further investigation.

It must not automatically become the root cause.

# 6. Hypothesis Status

The model defines:

```text
PROPOSED
TESTING
SUPPORTED
WEAKENED
REJECTED
```

Conceptually:

```text
PROPOSED
    ↓
TESTING
    ↓
SUPPORTED / WEAKENED / REJECTED
```

The current generator creates hypotheses in:

```text
proposed
```

status.

Later B18 components can evaluate and transition the status according to additional evidence.

---

# 7. Supporting Evidence

A hypothesis records the evidence that currently supports it.

Example:

```text
HYP-001
Supporting Evidence:
- E-001
- E-002
- E-003
```

This provides evidence traceability.

An investigator can determine which observations contributed to the proposed explanation.

---

# 8. Contradicting Evidence

A hypothesis also supports explicit contradicting evidence.

Example:

```text
Supporting:
- E-001
- E-002

Contradicting:
- E-007
```

This is important because an investigation should not only collect evidence that agrees with a theory.

Evidence that conflicts with a hypothesis must remain visible.

B18.6 prevents the same evidence ID from being simultaneously classified as both supporting and contradicting evidence.

---

# 9. Confidence

Confidence is optional.

```text
confidence = None
```

means confidence has not yet been established.

This is intentionally different from:

```text
confidence = 0.0
```

which represents an explicit zero-confidence value.

When present, confidence must be between:

```text
0.0 and 1.0
```

B18.6 does not automatically establish root-cause confidence.

Later investigation stages are responsible for evaluating evidence strength.

---

# 10. Affected Resources

A hypothesis records resources associated with the correlated evidence.

Examples:

```text
deployment/api
pod/api-1
container/api
server/server-b-tap
```

This supports the TAP requirement to identify where an incident appears to be occurring.

The resource recorded at this stage is an affected or correlated resource.

It is not automatically the root-cause location.

---

# 11. Reasoning

The model contains a reasoning field.

The current deterministic generator records why a hypothesis was created.

Example:

```text
The hypothesis was generated because the evidence
items belong to the same correlation group. This
establishes a possible relationship, not causation.
```

This makes generation behavior explainable.

---

# 12. Hypothesis Generator

Implementation:

```text
modules/B18/engine/hypothesis_generator.py
```

The generator accepts:

```text
CorrelationGroup
+
Evidence
```

and produces:

```text
list[Hypothesis]
```

The current implementation:

1. validates the correlation group
2. indexes available evidence
3. selects evidence belonging to the correlation group
4. identifies affected resources
5. preserves evidence IDs
6. creates a structured hypothesis
7. validates the resulting hypothesis
8. returns the hypothesis

---

# 13. Deterministic Initial Design

B18.6 intentionally begins with deterministic hypothesis generation.

This provides:

* reproducibility
* predictable behavior
* testability
* evidence traceability
* controlled development
* clear separation from AI reasoning

The system does not currently ask an AI model to invent arbitrary root causes.

AI-assisted hypothesis generation can be introduced later through the TAP AI Gateway and controlled prompt-engineering layer.

---

# 15. Security and Authority Boundary

B18.6 is an investigation component.

It does not:

* execute shell commands
* modify Kubernetes resources
* modify files
* restart services
* run Ansible
* run Terraform
* change firewall rules
* change infrastructure
* authorize remediation

The component produces structured investigation data only.

Any remediation that may later be recommended must pass through the TAP authorization and execution architecture.

---

# 17. Current Limitations

The current implementation deliberately has limited reasoning capability.

It currently generates a generalized possible explanation from a correlation group.

It does not yet:

* determine causality
* rank competing hypotheses
* automatically reject hypotheses
* perform evidence sufficiency analysis
* perform root cause analysis
* perform impact analysis
* generate remediation recommendations
* use AI models
* execute remediation

These capabilities belong to later B18 layers.

---

# 18. Relationship to B18.5

B18.5 determines whether evidence items are related.

Conceptually:

```text
B18.5
Correlation
"What evidence is related?"

        ↓

B18.6
Hypothesis
"What might explain the related evidence?"
```

Correlation identifies a relationship.

Hypothesis Generation proposes a possible explanation for that relationship.

The explanation remains provisional.

---

# 19. Relationship to B18.7

B18.7 will introduce evidence sufficiency.

Its purpose will be to determine whether the available evidence is strong enough to support further investigation conclusions.

Conceptually:

```text
Hypothesis
    ↓
Supporting Evidence
    ↓
Contradicting Evidence
    ↓
Evidence Sufficiency
    ↓
Supported / Insufficient / Rejected
```

This prevents a weak hypothesis from automatically becoming a root-cause conclusion.

---

# 20. Relationship to B18.8 RCA

B18.8 will perform Root Cause Analysis.

The distinction is:

```text
B18.6
Possible explanation

B18.7
Is there enough evidence?

B18.8
What explanation is sufficiently supported?
```

Therefore B18.6 must not claim that it has identified the root cause.

# 27. Investigation Principle

The current B18 investigation chain can be summarized as:

```text
Evidence
    = What was observed

Timeline
    = When it happened

Correlation
    = What observations are related

Hypothesis
    = What might explain them

Evidence Sufficiency
    = Is there enough evidence?

Root Cause
    = What explanation is sufficiently supported?

Recommendation
    = What should potentially be done?

Authorization
    = Is the action permitted?

Execution
    = Perform the authorized action

Verification
    = Did the action work?

Recorder
    = What was observed, decided, executed, and verified?
```

B18.6 implements the Hypothesis stage only.
