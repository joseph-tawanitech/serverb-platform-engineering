# B18.3 — Evidence Normalization

## 1. Module

**Server B / Tawanitech Automation Platform (TAP)**

**Status:** PASS

## 2. Objective

B18.3 introduces a normalization layer between evidence collectors and the B18 investigation pipeline.

The objective is to make evidence from different providers sufficiently consistent for downstream timeline construction, correlation and investigation while preserving the original provider-specific evidence content.

The core principle is:

**Normalize for correlation, preserve for investigation.**

## 5. Normalization Rules

### 5.1 Source Normalization

Source names are stripped of surrounding whitespace and converted to lowercase.

Example:

```text
"  Prometheus  "
```

becomes:

```text
"prometheus"
```

This provides consistent source identity across collectors.

---

## 6. Timestamp Normalization

B18.3 converts timezone-aware timestamps to UTC.

The following timestamps are normalized:

* `collected_at`
* `observation_time`

Example:

```text
2026-09-21 10:00 +02:00
```

becomes:

```text
2026-09-21 08:00 UTC
```

This provides a common time reference for future incident timelines and correlation.

Timezone-naive timestamps are rejected.

This prevents ambiguous timestamps from entering the investigation pipeline.

---

## 7. Resource Normalization

B18.3 applies basic normalization to resource identifiers.

For structured resource identifiers containing `/`, the resource type is normalized to lowercase while preserving the resource name.

Example:

```text
"  POD/API-7D8F  "
```

becomes:

```text
"pod/API-7D8F"
```

For resource identifiers without a type separator, surrounding whitespace is removed and the identifier is converted to lowercase.

Example:

```text
"  SERVER-B  "
```

becomes:

```text
"server-b"
```

This establishes a consistent basic representation for downstream correlation.

---

## 8. Preservation of Evidence Content

Normalization does not rewrite or discard the provider-specific `content` field.

Example:

```text
{
    "metric": "cpu_usage",
    "value": 94
}
```

remains unchanged after normalization.

This is important because normalization should make evidence easier to correlate without destroying the information needed for investigation.

Therefore:

**Common representation + preserved source-specific content**

is the B18 design approach.

---

## 9. Multi-Collector Context

B18 is designed to receive evidence from multiple collectors.

Potential sources include:

```text
Prometheus
Kubernetes
OTel
Logs
EDA
MCP
Future infrastructure collectors
```

Different providers may represent the same operational resource or event differently.

For example:

```text
Prometheus:
pod="api-7d8f"

Kubernetes:
metadata.name="api-7d8f"

Logs:
container="api-7d8f"
```

B18.3 provides the normalization foundation required for these observations to be represented consistently enough for later correlation.

The current implementation provides basic source, time and resource normalization. Provider-specific normalization rules can be added as future collectors and evidence types are implemented.

B16 is the AI-SRE Operations Console.

A common normalized evidence representation will allow B16 to consume information from multiple infrastructure and observability sources without requiring the dashboard to understand every provider-specific representation.

B16 can therefore become a consumer of the common evidence layer rather than a direct interface to every individual monitoring system.

---

## 13. Relationship to AI Reasoning

The normalization layer does not perform root-cause reasoning.

Its purpose is to improve the quality and consistency of the evidence provided to downstream investigation components.

The separation is:

```text
Collectors
    ↓
Evidence
    ↓
Normalization
    ↓
Correlation / Investigation
    ↓
AI Reasoning
```

This prevents the AI model from having to interpret an uncontrolled mixture of provider-specific formats at the first stage of investigation.

---

## 14. Security and Authority Boundary

B18.3 is an evidence-processing component.

It does not:

* authorize infrastructure changes
* execute remediation
* provide shell access
* grant AI execution authority

The TAP authority boundary remains separate.

The evidence layer prepares information for investigation; authorization and execution remain governed by TAP control mechanisms.

## 19. Design Principles

### Provider Independence

Normalization is separated from individual collection providers.

### Common Structure

Evidence receives a consistent representation before downstream investigation.

### Evidence Preservation

Provider-specific content is retained.

### Time Consistency

Timezone-aware timestamps are converted to UTC.

### Resource Consistency

Basic resource naming is normalized for downstream correlation.

### Separation of Concerns

Collection, normalization, investigation and execution remain separate responsibilities.

---

## 20. Current Limitations

The current B18.3 implementation provides foundational normalization only.

It does not yet implement:

* provider-specific schema adapters
* advanced resource identity resolution
* evidence deduplication
* cross-source conflict resolution
* semantic event normalization
* persistence
* evidence retrieval API
* automated cross-source correlation

These are future extensions of the TAP Evidence Layer and subsequent B18 stages.
