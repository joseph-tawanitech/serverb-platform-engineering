# B18.1 — Incident Data Model

## 1. Objective

Define a reusable, structured, and reproducible incident data model for the B18 Incident Investigation and Root Cause Analysis subsystem.

B18.1 establishes the foundational data contract that subsequent B18 layers will use for evidence collection, normalization, timeline construction, correlation, hypothesis generation, root-cause analysis, impact analysis, and recommendation generation.

---

## 2. Scope

B18.1 implements:

* Python Incident data model
* Incident severity enumeration
* Incident lifecycle status enumeration
* Evidence reference model
* Incident validation
* JSON Schema Draft 2020-12
* Automated model tests
* Automated JSON Schema validation tests

---

## 3. Incident Data Model

The B18 Incident model contains the following fields:

| Field                | Purpose                                                 |
| -------------------- | ------------------------------------------------------- |
| `incident_id`        | Unique identifier for the incident                      |
| `title`              | Human-readable incident title                           |
| `severity`           | Incident severity classification                        |
| `status`             | Current incident investigation lifecycle state          |
| `detected_at`        | Time the incident was detected                          |
| `source`             | System or mechanism that detected/reported the incident |
| `affected_resources` | Infrastructure or application resources affected        |
| `symptoms`           | Observed symptoms                                       |
| `evidence`           | Structured evidence references                          |
| `timeline`           | Chronological investigation events                      |
| `impact`             | Recorded impact information                             |
| `hypotheses`         | Possible explanations under investigation               |
| `root_cause`         | Identified root cause, when established                 |
| `recommendations`    | Recommended actions                                     |
| `confidence`         | Confidence associated with the investigation result     |
| `metadata`           | Additional contextual information                       |

---

## 4. Severity Model

B18 defines the following incident severity levels:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

Severity describes the assessed seriousness of the incident.

It does not independently authorize remediation.

---

## 5. Incident Lifecycle

B18 defines the following incident statuses:

```text
DETECTED
TRIAGED
INVESTIGATING
ROOT_CAUSE_IDENTIFIED
RECOMMENDATION_READY
RESOLVED
CLOSED
```

The status represents the investigation lifecycle and does not represent execution authorization.

---

## 6. Evidence Reference Model

B18 incidents reference evidence through structured evidence objects.

An evidence reference contains:

* `evidence_id`
* `source`
* `description`
* `collected_at`
* `location`
* `metadata`

This allows B18 to reference evidence from multiple systems without embedding all raw evidence directly inside the Incident object.

Future evidence sources may include:

```text
Kubernetes
Prometheus
OpenTelemetry
Logs
systemd
EDA
Network telemetry
Application telemetry
Cloud infrastructure
```

## 7. Design Principles

### 7.1 Symptoms Are Not Root Cause

B18 records observed symptoms separately from the eventual root cause.

Example:

```text
Symptom:
API unavailable

Root Cause:
Not yet established
```

The investigation must not assume that an observed symptom is automatically the root cause.

---

### 7.2 Evidence Is Referenced

Incident records contain structured evidence references.

Raw evidence can remain in the appropriate evidence subsystem while B18 maintains the references required for investigation.

---

### 7.3 Confidence Is Optional

The following states are intentionally different:

```text
confidence = null
```

means confidence has not yet been established.

Whereas:

```text
confidence = 0.0
```

represents an explicitly assigned zero-confidence value.

This distinction prevents an unknown investigation state from being incorrectly interpreted as zero confidence.

---

### 7.4 Investigation Before Remediation

B18 is an investigation and recommendation subsystem.

It does not independently execute infrastructure remediation.

---

## 8. JSON Schema

B18.1 defines a JSON Schema using:

```text
JSON Schema Draft 2020-12
```

Schema location:

```text
modules/B18/schemas/incident.schema.json
```

The schema provides a language-independent contract for incident records.

This allows other B18 components or future services to validate incident data without depending directly on the Python implementation.

---

## 9. Python Implementation

Primary implementation:

```text
modules/B18/engine/incident_model.py
```

The Python implementation provides:

* Incident data structures
* Severity enumeration
* Status enumeration
* Evidence reference structure
* Runtime validation

Python therefore provides the implementation and behavior of the B18 incident model, while JSON Schema provides the external data contract.

```text

```

Result:

```text

```

A schema/test mismatch was also detected during implementation.

The `impact` field was defined by the schema as an array while the initial test fixture supplied an object.

The mismatch was corrected by changing the fixture to:

```text
"impact": []
```

The complete test suite was subsequently rerun successfully:

```text

```

This demonstrates that the schema contract is actively tested rather than merely created.

## 16. Execution Boundary

B18 does not independently perform remediation.

The TAP control boundary remains:

```text
MONITOR
    |
DETECT
    |
REASON
    |
DECIDE
    |
AUTHORIZE
    |
EXECUTE
    |
VERIFY
    |
REPORT
```

B18 primarily operates within:

```text
DETECT
   |
REASON
   |
DECIDE
```

The resulting recommendation must pass through the appropriate TAP governance and authorization controls before execution.

Governed execution remains the responsibility of the appropriate TAP execution layer, such as the Job Broker, Ansible, Kubernetes, or Terraform.
