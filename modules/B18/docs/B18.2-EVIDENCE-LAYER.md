## 2. Objective

B18.2 establishes the foundational evidence layer for the B18 Incident Investigation and Root Cause Analysis engine.

The purpose of B18.2 is to provide a structured, validated and provider-independent representation of infrastructure evidence and a common collector interface through which evidence can be obtained.

The design prevents the B18 investigation engine from becoming tightly coupled to a specific monitoring or infrastructure technology.

B18.2 establishes the foundation for the future:

**TAP Evidence Layer / Evidence API Architecture**

---

## 3. Architectural Position

The B18 investigation architecture is designed around a separation between evidence collection and investigation/reasoning.

```text
Infrastructure / Operational Sources
              |
      Provider Collectors
              |
              v
       B18 Evidence Model
              |
        Evidence Schema
              |
              v
       Evidence Layer/API
              |
       +------+------+
       |             |
       v             v
      B16           B18
   AI-SRE Console   Investigation
       |
       v
   AI Gateway / AI Models
```

The collector interface allows different evidence providers to be integrated without changing the B18 investigation engine.

## 4. Evidence Model

The implementation is located at:

```text
modules/B18/engine/evidence_model.py
```

The `Evidence` model represents one structured piece of operational or infrastructure evidence.

The model contains:

* `evidence_id`
* `source`
* `evidence_type`
* `collected_at`
* `observation_time`
* `resource`
* `content`
* `location`
* `reliability`
* `status`
* `metadata`

This provides a common structure for evidence originating from different systems.

---

## 5. Evidence Types

B18.2 defines the following evidence types:

* `metric`
* `log`
* `trace`
* `event`
* `kubernetes_state`
* `command_output`
* `configuration`
* `alert`
* `other`

The model is intentionally provider-independent.

For example, a Kubernetes collector and a Prometheus collector can both produce `Evidence` objects while retaining their own source identity and metadata.

---

## 6. Evidence Reliability

Evidence reliability is explicitly represented using:

* `unknown`
* `low`
* `medium`
* `high`

This allows later investigation stages to distinguish between evidence that is highly trusted and evidence that may require additional verification.

Reliability is evidence metadata and does not itself establish root cause.

---

## 7. Evidence Status

B18.2 defines:

* `collected`
* `partial`
* `failed`

This allows the investigation system to distinguish successful evidence collection from incomplete or failed collection.

This is important for future evidence-sufficiency analysis.

An investigation should be able to identify when conclusions are being made from incomplete evidence.

---

## 8. Evidence JSON Schema

The JSON Schema is located at:

```text
modules/B18/schemas/evidence.schema.json
```

The schema uses:

```text
JSON Schema Draft 2020-12
```

Schema identifier:

```text
https://tawanitech.local/schemas/b18/evidence.schema.json
```

The schema defines the required evidence fields, enumerated evidence types, reliability values, status values and date-time formats.

The schema also uses:

```text
additionalProperties: false
```

to prevent undocumented fields from silently entering the structured evidence contract.

---

## 9. Evidence Content

The `content` field is intentionally flexible.

Infrastructure evidence can have different structures depending on the source.

Examples include:

* Prometheus metric results
* Kubernetes resource state
* log records
* OTel trace information
* EDA events
* command output
* configuration information
* alert payloads

The evidence model therefore provides a common envelope while allowing source-specific evidence content.

---

## 10. Provider-Independent Collector Interface

The collector interface is implemented in:

```text
modules/B18/engine/evidence_collector.py
```

The main abstraction is:

```text
EvidenceCollector
```

The collector contract exposes:

```text
source
collect(query)
```

The investigation engine does not need to know whether evidence came from Kubernetes, Prometheus, OTel, logs, MCP or another provider.

It requests evidence through the common collector contract.

This provides provider independence.

## 11. Static Evidence Collector

B18.2 includes:

```text
StaticEvidenceCollector
```

This is a simple implementation used for controlled testing.

It allows predefined evidence to be returned through the same collector interface used by future real providers.

This provides a deterministic test mechanism without requiring live monitoring systems during unit testing.

## 15. Relationship to B18

B18 uses evidence as the foundation for:

```text
Evidence
    |
    v
Timeline
    |
    v
Symptoms
    |
    v
Correlation
    |
    v
Hypotheses
    |
    v
Evidence Sufficiency
    |
    v
Root Cause
    |
    v
Recommendations
```

B18 must distinguish observed evidence from conclusions generated during investigation.

Evidence is therefore stored separately from:

* symptoms
* hypotheses
* root cause
* recommendations
* confidence

This separation reduces the risk of treating an AI-generated conclusion as if it were an observed fact.

## 16. Relationship to AI Gateway

The AI Gateway provides controlled access to AI models.

The Evidence Layer provides structured evidence to systems that require it.

The responsibilities remain separate:

```text
Evidence Layer
    |
    | provides evidence
    v
AI Gateway
    |
    | provides controlled model access
    v
AI Model
```

The AI model does not become the authoritative source of infrastructure evidence.

Evidence must originate from controlled infrastructure and operational sources.

## 17. Security and Authority Boundary

B18.2 is an evidence and investigation foundation.

It does not provide remediation authority.

The B18 investigation engine may eventually produce:

* hypotheses
* root-cause assessments
* recommendations
* confidence assessments

but execution remains outside B18.

Governed execution remains the responsibility of TAP's authorization and execution layers.

The intended TAP control model remains:

```text
MONITOR
   ↓
DETECT
   ↓
REASON
   ↓
DECIDE
   ↓
AUTHORIZE
   ↓
EXECUTE
   ↓
VERIFY
   ↓
REPORT
```

B18 primarily operates within:

```text
DETECT → REASON → DECIDE
```

while remaining subject to TAP authorization boundaries.

## 22. Design Principles

B18.2 establishes the following principles:

### Provider Independence

The investigation engine does not depend on one monitoring or infrastructure provider.

### Structured Evidence

Evidence follows a defined model and schema.

### Evidence Before Reasoning

Investigation reasoning should be based on collected evidence.

### Separation of Evidence and Conclusions

Observed evidence is distinct from hypotheses, root cause and recommendations.

### Extensibility

New evidence providers can be integrated through the collector interface.

### Testability

Static evidence can be injected through the collector interface for deterministic testing.

### Governed Execution

Evidence and AI reasoning do not automatically grant execution authority.
