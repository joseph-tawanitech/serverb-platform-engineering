## 1. Objective

B18.5 introduces a deterministic evidence-correlation layer for incident investigation.

The purpose of correlation is to identify relationships between separate evidence records that may describe the same incident context, resource, or event.

Correlation does not establish root cause.

B18.5 therefore operates between the timeline layer and later investigation reasoning:

INCIDENT
→ EVIDENCE
→ NORMALIZATION
→ TIMELINE
→ CORRELATION
→ HYPOTHESES
→ EVIDENCE SUFFICIENCY
→ ROOT CAUSE ANALYSIS

## 4. Correlation Concept

Correlation means identifying evidence items that are related according to defined rules.

Example:

10:01:12 — Kubernetes reports an API pod restart.

10:01:18 — Prometheus reports high CPU for the same workload.

10:01:21 — Logs report a database connection error.

10:01:25 — OTel reports increased application latency.

Individually, these observations describe different aspects of the environment.

Correlation asks whether the observations are related through shared context such as:

* the same resource;
* the same workload or service;
* the same incident;
* the same time period;
* related metadata;
* another explicitly defined relationship.

Correlation therefore connects evidence without prematurely declaring causation.

---

## 5. CorrelationLink

`CorrelationLink` represents a relationship between two evidence items.

Fields:

* `source_evidence_id`
* `related_evidence_id`
* `reason`
* `confidence`
* `metadata`

Every link must identify the two evidence records involved.

Every link must provide an explanation for why the relationship exists.

Confidence is represented from 0.0 to 1.0.

Self-correlation is rejected.

An evidence item cannot be correlated with itself.

---

## 6. CorrelationGroup

`CorrelationGroup` represents a set of evidence items connected through correlation links.

Fields:

* `correlation_id`
* `evidence_ids`
* `links`
* `metadata`

Evidence identifiers must be unique within a group.

A group must contain at least one evidence identifier.

Correlation groups preserve traceability back to the original evidence records.

---

## 7. Deterministic Correlation Rules

The initial B18.5 implementation uses deterministic rules rather than AI reasoning.

### Rule 1 — Same Resource and Time Window

Two evidence items are strongly correlated when:

* they reference the same resource; and
* their observation timestamps fall within the configured time window.

The default test configuration uses a five-minute window.

This relationship receives a confidence value of `0.95`.

Reason:

`Same resource within the configured time window`

### Rule 2 — Same Resource

Two evidence items may still be correlated when they reference the same resource even when they fall outside the configured time window.

This relationship receives a lower confidence value of `0.80`.

Reason:

`Same resource`

This represents a relationship, not proof that both observations belong to the same causal chain.

### Rule 3 — Different Resources

Evidence referring to different resources does not receive a same-resource correlation from the current engine.

### Rule 4 — Missing Resource

When resource identity is unavailable, the current engine does not create a same-resource correlation.

This prevents the engine from inventing a relationship from insufficient resource information.

---

## 8. Time Window

The correlation engine accepts a configurable time window in seconds.

Example:

`time_window_seconds=300`

represents five minutes.

Negative time windows are rejected.

Observation time is preferred when available.

Collected time is used when observation time is unavailable, following the B18 evidence model and timeline construction rules.

---

## 9. Correlation Confidence

Correlation confidence expresses the strength of the detected relationship.

It does not represent root-cause confidence.

For example:

`0.95` means the implemented correlation rule found strong supporting conditions.

It does not mean:

`95% probability that this evidence caused the incident.`

This distinction is required to prevent correlation confidence from being incorrectly interpreted as causal certainty.

---

## 10. Group Construction

The correlation engine builds links between related evidence items and then constructs connected evidence groups.

For example:

Evidence A correlates with Evidence B.

Evidence B correlates with Evidence C.

The engine can therefore place:

Evidence A + Evidence B + Evidence C

into one correlation group.

The original evidence IDs remain available for traceability.

---

## 11. Explainability

B18.5 is intentionally explainable.

The system records why a relationship was created.

Example:

`Same resource within the configured time window`

This allows a later investigator, reviewer, or auditor to understand the basis for the relationship without relying on opaque AI reasoning.

---

## 12. Correlation Is Not Causation

This is a fundamental B18 design principle.

Correlation answers:

"Are these observations related?"

It does not answer:

"Which observation caused the incident?"

For example:

Pod restart
+
CPU 94%
+
Database connection refused

may be correlated.

B18.5 must not conclude:

"Database connectivity caused the incident."

A later investigation stage must evaluate evidence, generate hypotheses, assess evidence sufficiency, and determine whether a root-cause conclusion is supported.

---

## 13. Relationship to B18.4 Timeline

B18.4 answers:

"What happened, and in what chronological order?"

B18.5 answers:

"Which observations are related?"

The timeline provides temporal structure.

Correlation adds relationship structure.

Together they create a stronger investigation input for subsequent B18 stages.

## 14. Relationship to B18.6

B18.6 Hypothesis Generation will consume correlated evidence.

A hypothesis is a possible explanation for the observed symptoms and evidence.

Examples may include:

* database connectivity failure;
* resource exhaustion;

B18.6 may use AI-assisted reasoning through the governed TAP AI architecture.

B18.5 itself remains deterministic.

---

## 15. Security and Authority Boundary

B18.5 is an investigation component.

It has no remediation authority.

The correlation engine:

* reads evidence;
* analyzes relationships;
* creates correlation records;
* produces structured investigation data.

It does not:

* modify infrastructure;
* restart services;
* delete resources;
* apply Kubernetes changes;
* run Ansible;
* run Terraform;
* bypass authorization;
* execute remediation.

This preserves the TAP principle:

AI and investigation systems may reason about infrastructure, while TAP governance controls authority and execution.

## 21. Current Limitations

The first B18.5 implementation intentionally uses a limited deterministic rule set.

Current correlation focuses primarily on:

* resource identity;
* temporal proximity.

Future correlation capabilities may include:

* service identity;
* namespace relationships;
* workload ownership;
* pod/container relationships;
* dependency relationships;
* network endpoints;
* deployment/change events;
* shared configuration;
* log-event relationships;
* trace relationships;
* cross-source semantic relationships;
* evidence deduplication;
* stronger multi-source corroboration.

These extensions must preserve explainability and evidence traceability.

---

## 22. Future AI-Assisted Correlation

AI may later assist with more complex relationships where deterministic rules are insufficient.

For example, AI could identify that:

a deployment change,

a sudden latency increase,

a database error,

and a Kubernetes restart

appear semantically related.

However, the AI-generated relationship should remain a hypothesis or recommendation for investigation unless supported by sufficient evidence.

The TAP authority boundary remains unchanged.

## 23. Design Principle

The B18.5 design follows:

**Correlate first. Explain the relationship. Preserve the evidence. Establish causality later.**

This prevents premature RCA conclusions and provides a structured foundation for investigation.
