# B19.2 — Multi-Source RAG Architecture

## 1. Overview

B19.2 establishes the architectural model for a **multi-source Retrieval-Augmented Generation (RAG) layer** within TAP.

RAG is not limited to static documents. The architecture allows B19 to retrieve relevant information from controlled infrastructure, observability, security, network, business, and historical knowledge sources.

The purpose of B19 is to provide relevant information and context to the AI reasoning layer while preserving the TAP authority boundary.

## 2. Multi-Source Retrieval Concept

B19 can work with information retrieved through controlled interfaces such as:

* MCP
* APIs
* Connectors
* Files
* Databases
* Future controlled retrieval mechanisms

Potential information sources include:

* Kubernetes
* Prometheus
* Logs
* OpenTelemetry
* Network systems
* Security systems
* Terraform
* Ansible
* Incident history
* RCA records
* ITSM
* CMDB
* Git
* Cloud platforms
* Storage systems
* Websites
* Business systems
* CCTV and other authorized systems

The architecture does not require every source to be implemented immediately. Instead, B19 establishes a scalable retrieval model that can support additional sources as the platform evolves.

## 4. Relationship With Other TAP Components

B19 does not replace the systems that produce operational information.

Instead:

**Observability systems observe.**

**Kubernetes exposes cluster state.**

**Prometheus provides metrics.**

**Logs and OTel provide operational evidence.**

**Security systems provide security information.**

**Terraform and Ansible provide infrastructure and configuration information.**

**MCP, APIs, and connectors provide controlled access to information.**

**B19 retrieves, correlates, ranks, and assembles relevant context.**

**B18 structures and validates incident evidence.**

**B17 structures the AI context and prompt.**

**B15 AI Gateway provides controlled model access.**

**The AI reasons over the available context.**

**TAP governs decisions and actions.**

## 5. RAG and Incident Evidence

B19 may retrieve information that is relevant to an incident investigation.

However, retrieved information should not automatically become authoritative incident evidence.

The B18 Incident Layer remains responsible for evidence validation and incident association.

The intended relationship is:

```text
Information Sources
        ↓
Controlled Retrieval
        ↓
B19 RAG
        ↓
Relevant Information
        ↓
B18 Incident Layer
        ↓
Evidence Validation
        ↓
Incident Association
        ↓
Timeline / Impact / Investigation
        ↓
AI Reasoning
```

This preserves separation between retrieval and incident management.

## 6. Provenance and Traceability

Retrieved information should retain sufficient provenance to identify:

* Source
* Source type
* Collection or retrieval time
* Resource
* Incident association where applicable
* Version where applicable
* Reference or identifier
* Tenant or ownership context
* Access-control context

This allows TAP to answer:

> Where did this information come from?

and:

> Why was this information included in the investigation context?

## 7. Security and Tenant Isolation

Multi-source retrieval must preserve authorization and tenant boundaries.

Information belonging to one customer or environment must not automatically become available to another customer.

RAG retrieval therefore operates within controlled access boundaries.

Retrieved knowledge is context for reasoning. It does not grant execution authority.

## 8. Execution Boundary

B19 does not execute infrastructure changes.

The architecture remains:

```text
Retrieve
   ↓
Reason
   ↓
Recommendation
   ↓
TAP DECIDE
   ↓
AUTHORIZE
   ↓
EXECUTE
   ↓
VERIFY
   ↓
REPORT
```

An AI agent may eventually use information retrieved through B19 to recommend or request an action, but TAP remains the authority boundary.

## 12. Completion Status

**B19.2 — PASS**

B19 now has a defined multi-source retrieval architecture capable of expanding beyond document-based RAG.

The architectural principle is:

> **Information sources provide information → controlled interfaces expose information → B19 retrieves and correlates → B18 structures and validates incident evidence → B17 provides context → B15 controls AI access → AI reasons → TAP governs decisions and actions.**


Framework-Neutral Design

B19.2 does not require a specific RAG or AI orchestration framework. Future implementations may use native Python components, LangChain, LlamaIndex, or another suitable framework where justified by actual platform requirements.

Such frameworks remain optional implementation components. They do not replace the B19 RAG boundary, MCP controlled interfaces, AI Gateway, or TAP governance and authorization model.

LangChain is therefore intentionally deferred from the current B19.2 deployment until a concrete requirement exists for advanced workflow or model orchestration
