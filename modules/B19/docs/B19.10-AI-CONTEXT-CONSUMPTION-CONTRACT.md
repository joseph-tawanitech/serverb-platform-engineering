## 1. Purpose

B19.10 establishes the controlled interface between the deterministic RAG context layer and future AI investigation.

B19.8 determines which knowledge is relevant.

B19.9 assembles that retrieved knowledge into a deterministic `RAGContext`.

B19.10 defines how that assembled context is handed to a future AI consumer.

The purpose is to create a stable, provider-neutral boundary between:

```text
RAG Knowledge
     ↓
RAG Context
     ↓
AI Context Request
     ↓
Future AI Investigation
```

B19.10 does not perform AI reasoning.

---

> **B19.10 defines how RAG knowledge is handed to AI; it does not define what the AI thinks about that knowledge.**

This distinction is fundamental to TAP.

RAG prepares knowledge.

TAP governs consequential decisions and authority.

## 5. AIContextRequest

The primary B19.10 model is:

```text
AIContextRequest
```

It contains:

```text
request_id
investigation_id
purpose
context
created_at
```

### request_id

Uniquely identifies the AI-context consumption request.

Example:

```text
AICTX-001
```

---

### investigation_id

Associates the context request with a specific future investigation.

Example:

```text
INV-001
```

This enables future end-to-end traceability:

```text
INCIDENT-001
    ↓
INV-001
    ↓
RAG QUERY
    ↓
RAG CONTEXT
    ↓
AICTX-001
    ↓
AI INVESTIGATION
```

---

### purpose

Describes why the AI context is being consumed.

Examples:

```text
AI incident investigation
RCA investigation
configuration investigation
security investigation
```

The purpose is descriptive metadata.

It does not grant authority.

---

### context

Contains the validated B19.9 `RAGContext`.

B19.10 does not rebuild or modify the context.

It preserves the already assembled deterministic knowledge package.

---

### created_at

Records when the AI-context request was created.

This provides an additional temporal reference for future investigation and audit trails.

---

## 6. Validation

B19.10 validates the complete request boundary.

Validation requires:

* non-empty `request_id`
* non-empty `investigation_id`
* non-empty `purpose`
* valid `RAGContext`
* valid `created_at`
* valid nested context structure

Invalid context types are rejected.

Invalid identity values are rejected.

Invalid timestamps are rejected.

The underlying `RAGContext` remains responsible for its own internal validation.

This creates layered validation:

```text
AIContextRequest
      ↓
validate request metadata
      ↓
validate RAGContext
      ↓
validated AI context boundary
```
