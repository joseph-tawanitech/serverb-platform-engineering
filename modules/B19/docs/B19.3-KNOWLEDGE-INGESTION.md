# B19.3 — Knowledge Ingestion

## 1. Overview

B19.3 establishes the controlled knowledge ingestion boundary for the
Tawanitech Automation Platform (TAP) RAG layer.

The purpose of this module is to provide a deterministic and validated
entry point through which knowledge can enter the B19 knowledge layer.

The ingestion boundary validates:

- KnowledgeDocument structure
- Knowledge provenance
- Document and provenance types
- Required metadata
- Source traceability

B19.3 does not yet implement:

- Embeddings
- Vector databases
- Semantic search
- Retrieval ranking
- AI reasoning
- Infrastructure execution
- Authorization
- External production source connectors

B19.3 therefore establishes the foundation required for later RAG
retrieval capabilities without introducing execution authority.

---

## 2. Objective

The objective of B19.3 is to ensure that knowledge entering the TAP
RAG system is:

1. Structurally valid
2. Associated with a known source
3. Associated with provenance information
4. Validated before entering the knowledge layer
5. Deterministically represented
6. Traceable for future retrieval and audit operations

The design follows the TAP principle:

> AI proposes; TAP controls.

Knowledge ingestion prepares information for later AI-assisted retrieval.
It does not grant the AI authority to modify infrastructure.

---

## 3. B19 RAG Position

The B19 architecture separates ingestion from retrieval and reasoning.

The current flow is:

    Source
      |
      | file / API / MCP / database / connector
      v
    B19 Knowledge Ingestion
      |
      +-- Validate document
      |
      +-- Validate provenance
      |
      +-- Capture source information
      |
      +-- Validate metadata
      |
      v
    B19 Knowledge Layer
      |
      v
    Future Retrieval
      |
      v
    B18 Incident / Evidence Context
      |
      v
    AI Reasoning
      |
      v
    TAP Governance

B19.3 implements the ingestion boundary only.

---

## 4. Controlled Ingestion Boundary

The `KnowledgeIngestor` class provides the controlled entry point.

Its responsibility is to receive:

- A `KnowledgeDocument`
- A `KnowledgeProvenance`

and validate both before returning an ingestion result.

The ingestion boundary therefore prevents arbitrary objects from being
treated as valid TAP knowledge.

The implementation performs type validation first and then invokes the
validation methods defined by the B19 knowledge model and provenance
model.

---

## 5. KnowledgeDocument

B19.3 uses the existing B19.1 `KnowledgeDocument` model.

A knowledge document represents information that can eventually become
part of the RAG knowledge base.

Examples include:

- Runbooks
- Architecture documentation
- Incident records
- RCA records
- Configuration information
- Procedures
- Infrastructure documentation
- Evidence records

The document contains metadata such as:

- Document ID
- Title
- Knowledge type
- Source type
- Content
- Source
- Creation time
- Version
- Resource
- Tags

B19.3 does not alter the underlying knowledge document model.

---

## 6. Knowledge Provenance

Every successfully ingested knowledge document is paired with
`KnowledgeProvenance`.

Provenance records where the information came from and provides
traceability information.

The provenance model includes:

- Source
- Source type
- Collection time
- Collector
- Version
- Checksum
- Reference

Provenance is important because retrieved knowledge must not simply be
treated as unexplained context.

The intended future RAG principle is:

    Retrieve
        |
        v
    Attribute
        |
        v
    Validate
        |
        v
    Correlate
        |
        v
    Reason

rather than:

    Retrieve
        |
        v
    Believe
        |
        v
    Act

B19.3 establishes the first part of this traceability chain.

---

## 7. IngestedKnowledge

B19.3 introduces the `IngestedKnowledge` result object.

It contains:

- The validated `KnowledgeDocument`
- The validated `KnowledgeProvenance`

This creates a deterministic representation of successfully ingested
knowledge.

Conceptually:

    IngestedKnowledge
    ├── document
    │   └── KnowledgeDocument
    │
    └── provenance
        └── KnowledgeProvenance

This structure can later be extended by subsequent B19 modules without
changing the basic ingestion boundary.

---

## 8. Validation

B19.3 performs validation before accepting knowledge.

The ingestion process is:

    KnowledgeDocument
            |
            v
      Type validation
            |
            v
      Document validation
            |
            v
    KnowledgeProvenance
            |
            v
      Type validation
            |
            v
     Provenance validation
            |
            v
      IngestedKnowledge

Invalid input is rejected.

Examples include:

- Invalid document object
- Invalid provenance object
- Empty document content
- Empty provenance source
- Invalid metadata

This prevents malformed information from silently entering the B19
knowledge layer.

## 10. KnowledgeIngestor Responsibilities

`KnowledgeIngestor` is responsible for:

- Receiving a knowledge document
- Receiving provenance
- Validating object types
- Validating the document
- Validating provenance
- Returning validated knowledge

It is not responsible for:

- Embedding generation
- Vector database operations
- Semantic retrieval
- LLM inference
- Prompt engineering
- Infrastructure discovery
- Infrastructure modification
- Authorization
- Remediation
- Job execution

These responsibilities remain separated into later TAP modules.

## 11. Source Independence

B19.3 remains source-independent.

The ingestion boundary can eventually receive knowledge originating from:

- Files
- APIs
- MCP
- Databases
- Incident systems
- Evidence stores
- ITSM systems
- CMDB systems
- Git repositories
- Kubernetes
- Prometheus
- OTel
- Security systems
- Cloud platforms
- Other controlled connectors

B19.3 does not directly connect to these systems yet.

Instead, future source adapters can transform source information into
the B19 knowledge model before submitting it to the ingestion boundary.

Conceptually:

    External Source
          |
          v
    Source Adapter
          |
          v
    KnowledgeDocument
          +
    KnowledgeProvenance
          |
          v
    KnowledgeIngestor
          |
          v
    B19 Knowledge Layer

This separation keeps external source integration independent from the
core ingestion validation logic.

## 14. Security Boundary

Knowledge ingestion is not an execution mechanism.

Successfully ingesting information does not provide authority to:

- Execute commands
- Modify Kubernetes
- Run Ansible
- Change Terraform
- Modify firewall rules
- Restart services
- Change users
- Access unrelated tenants
- Approve remediation

The ingestion layer is therefore separated from TAP execution authority.

The architectural boundary remains:

    Knowledge
        |
        v
    Retrieval
        |
        v
    AI Reasoning
        |
        v
    TAP Policy
        |
        v
    Authorization
        |
        v
    Job Broker
        |
        v
    Execution

B19.3 stops at the knowledge boundary.

## 15. Tenant Isolation

Future production ingestion must enforce tenant and access boundaries.

For example:

    Tenant A
      |
      +-- Knowledge
      +-- Incidents
      +-- RCA
      +-- Runbooks
      +-- Infrastructure history

    Tenant B
      |
      +-- Knowledge
      +-- Incidents
      +-- RCA
      +-- Runbooks
      +-- Infrastructure history

Knowledge belonging to one customer must not automatically become
available to another customer.

Shared knowledge must be explicitly classified and controlled.

Tenant isolation will be expanded in later B19 security and retrieval
modules.

- Version

These fields are important for future knowledge lifecycle management.

For example, a future ingestion pipeline could determine that a

another RAG framework.

Frameworks may be evaluated later if a concrete requirement emerges
for:

- Multi-step model pipelines

Any future framework remains below the TAP governance boundary.

A framework must not become the authority layer for infrastructure
execution.

## 26. Glossary

### Knowledge

Information that can be stored and later retrieved to provide context
for AI-assisted investigation or operations.

### KnowledgeDocument

The structured B19 representation of a knowledge item.

### Provenance

Information describing where knowledge originated, when it was
collected, who or what collected it, and how it can be traced back to
its source.

### Ingestion

The controlled process of accepting information into the B19 knowledge
layer after validation.

### Source

The original system, document, database, API, MCP service, or other
origin from which knowledge is obtained.

### Retrieval

The process of finding relevant knowledge for a particular question,
incident, or investigation.

### Embedding

A numerical representation of information that can be used for
similarity-based retrieval. Embeddings are not implemented in B19.3.

### Vector Store

A storage system used to store and search embeddings. Vector storage is
not implemented in B19.3.

### RAG

Retrieval-Augmented Generation: an architecture in which relevant
external knowledge is retrieved and supplied to an AI model as context.

### Tenant Isolation

The separation of one customer's knowledge and data from another
customer's knowledge and data.

### Authority

The permission to perform an action against infrastructure.

Knowledge ingestion does not grant authority.

### TAP Governance

The controls that determine whether AI-generated recommendations may
proceed through policy, authorization, execution, verification, and
recording.

## 27. Final Principle

B19.3 establishes an important separation in TAP:

> Knowledge can enter the system without giving AI the authority to act.

The RAG layer can therefore grow independently from the execution layer.

The intended architecture remains:

    Knowledge
       ↓
    Retrieval
       ↓
    Context
       ↓
    AI Reasoning
       ↓
    TAP Governance
       ↓
    Authorization
       ↓
    Controlled Execution
       ↓
    Verification
       ↓
    Recording

B19.3 establishes the controlled entry point for the first stage of
that architecture.
