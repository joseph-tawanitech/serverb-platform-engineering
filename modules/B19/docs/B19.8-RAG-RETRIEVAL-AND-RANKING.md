## 1. Overview

B19.8 establishes the first operational retrieval and ranking layer of the Server B RAG architecture.

The purpose of B19.8 is to answer a fundamental AI-SRE question:

> **Given an investigation question or incident context, which existing knowledge should be retrieved, and in what order should it be presented?**

Earlier B19 components established the foundations required for controlled retrieval:

* B19.1 — RAG foundation
* B19.2 — Multi-source RAG architecture
* B19.3 — Controlled knowledge ingestion
* B19.4 — Evidence indexing
* B19.7 — Provenance and content integrity

B19.8 builds on these components by introducing deterministic retrieval and ranking.

The resulting architecture is:

```text
External Knowledge Sources
        │
        ▼
B19.3 Controlled Ingestion
        │
        ▼
B19.4 Evidence Index
        │
        ▼
B19.7 Provenance + Integrity
        │
        ▼
B19.8 Retrieval + Ranking
        │
        ▼
Future RAG Context Assembly
        │
        ▼
AI Investigation / RCA
        │
        ▼
TAP Governance
```

B19.8 remains provider-neutral and does not require an AI model, embedding model, vector database, or external retrieval service.

---

# 2. Objective

The objective of B19.8 is to establish a controlled, deterministic, explainable retrieval mechanism that can:

1. Accept a structured retrieval query.
2. Search the B19.4 evidence index.
3. Select eligible knowledge candidates.
4. Filter candidates using structured metadata.
5. Rank candidates deterministically.
6. Return the highest-ranked results.
7. Preserve provenance information.
8. Support incident-specific retrieval.
9. Provide an explainable score breakdown.
10. Return predictable results for identical inputs.

B19.8 therefore establishes the first practical RAG retrieval contract for TAP.

---

# 3. Architectural Principle

The central B19.8 principle is:

> **Retrieve relevant knowledge before asking AI to reason over it.**

This establishes an important separation between observed evidence, existing knowledge, and AI reasoning.

```text
Evidence
   │
   │ tells AI what is happening
   ▼
Incident / System State
   │
   ▼
RAG Retrieval
   │
   │ retrieves what is already known
   ▼
Relevant Knowledge
   │
   ▼
AI Investigation
   │
   │ correlates evidence + knowledge
   ▼
Reasoning / RCA
   │
   ▼
TAP Governance
```

The distinction is:

> **Evidence tells AI what is happening.**

> **RAG retrieves what is already known about it.**

> **AI correlates the two and reasons about the incident.**

> **TAP controls what happens next.**

---

# 4. Relationship to B19.7

B19.7 established provenance and content integrity.

B19.8 consumes that information without treating provenance as a relevance signal.

This distinction is deliberate.

```text
Provenance
    │
    ├── Where did the knowledge come from?
    ├── Who collected it?
    ├── When was it collected?
    ├── What version was recorded?
    └── What checksum was recorded?
```

Retrieval relevance answers a different question:

```text
Relevance
    │
    ├── Does the resource match?
    ├── Does the knowledge type match?
    ├── Does the source type match?
    ├── Do the requested tags match?
    └── Does the title match the query?
```

Therefore:

> **Provenance establishes traceability; relevance establishes retrieval priority.**

B19.8 does not award relevance points merely because provenance exists.

# 7. RetrievalQuery

`RetrievalQuery` represents the structured request submitted to the retrieval engine.

The query contains:

```text
query_id
text
resource
knowledge_types
source_types
tags
incident_id
limit
```

Conceptually:

```text
RetrievalQuery
│
├── query_id
├── text
├── resource
├── knowledge_types[]
├── source_types[]
├── tags[]
├── incident_id
└── limit
```

## 7.1 Query ID

`query_id` uniquely identifies the retrieval request.

An empty query ID is rejected.

This supports future audit and retrieval tracing.

---

## 7.2 Query Text

The query contains human-readable investigation text.

Example:

```text
Kubernetes memory incident
```

The current deterministic engine uses query text primarily for title matching.

Future semantic retrieval can extend this without changing the fundamental query contract.

---

## 7.3 Resource Filter

A query can specify a target resource.

Example:

```text
resource="server-b-tap"
```

This allows retrieval to focus on knowledge associated with a specific infrastructure resource.

---

## 7.4 Knowledge Type Filter

Retrieval can be restricted to specific knowledge categories.

Examples include:

```text
incident
rca
procedure
runbook
documentation
configuration
```

This allows an AI-SRE investigation to distinguish between:

```text
Incident records
RCA records
Procedures
Runbooks
Documentation
```

---

## 7.5 Source Type Filter

Retrieval can also restrict results by knowledge source type.

Examples include:

```text
incident_record
evidence_store
file
database
mcp
api
```

This provides controlled source selection.

---

## 7.6 Tag Filter

Queries may specify tags such as:

```text
kubernetes
memory
network
recovery
security
```

Tags allow retrieval to narrow the knowledge domain.

---

## 7.7 Incident-ID Filter

B19.8 supports explicit incident-aware retrieval.

Example:

```text
incident_id="INC-001"
```

This is important for AI-SRE because an investigation may need to retrieve knowledge belonging specifically to the current incident.

The incident identifier is treated as structured metadata.

It is not inferred from arbitrary document content.

---

# 8. Incident-Aware Retrieval

B19.8 required a small extension to the B19.4 evidence index because `KnowledgeDocument` already supported:

```text
incident_id
```

but the evidence index did not previously preserve it.

The implemented flow is now:

```text
KnowledgeDocument
      │
      │ incident_id
      ▼
EvidenceIndexEntry
      │
      ▼
RetrievalEngine
      │
      │ incident_id filter
      ▼
RetrievalResult
```

Example:

```text
INC-001
```

can retrieve:

```text
DOC-INCIDENT-001
```

while excluding unrelated incident records.

An unknown incident returns an empty result set.

This provides deterministic incident isolation.

---

# 9. Candidate Selection

The retrieval engine first identifies eligible candidates from the B19.4 evidence index.

Filtering occurs before ranking.

Conceptually:

```text
Evidence Index
      │
      ▼
Resource filter
      │
      ▼
Knowledge type filter
      │
      ▼
Source type filter
      │
      ▼
Tag filter
      │
      ▼
Incident-ID filter
      │
      ▼
Eligible Candidates
```

This prevents irrelevant documents from participating in ranking.

---

# 10. Filtering Rules

The current implementation supports the following filters.

| Filter         | Purpose                                   |
| -------------- | ----------------------------------------- |
| Resource       | Restrict retrieval to a resource          |
| Knowledge type | Restrict the type of knowledge            |
| Source type    | Restrict the knowledge source             |
| Tags           | Restrict knowledge domain                 |
| Incident ID    | Restrict knowledge to a specific incident |

Filtering is deterministic.

The same indexed knowledge and the same query produce the same candidate set.

---

# 11. RetrievalCandidate

Candidates are represented internally as `RetrievalCandidate`.

A candidate contains:

```text
document_id
entry
matched_fields
```

`matched_fields` provides an internal representation of which retrieval attributes contributed to candidate matching.

This supports future explainability and audit improvements.

---

# 12. Deterministic Ranking

After filtering, eligible candidates are ranked.

The current ranking mechanism is deliberately deterministic.

The score weights are:

| Ranking factor       | Score |
| -------------------- | ----: |
| Resource match       |    30 |
| Knowledge type match |    20 |
| Source type match    |    15 |
| Tag match            |    15 |
| Title match          |    10 |

Maximum theoretical score:

```text
30 + 20 + 15 + 15 + 10 = 90
```

The exact ranking logic remains transparent and inspectable.

---

# 13. Resource Relevance

A matching resource receives the highest individual ranking weight:

```text
RESOURCE_SCORE = 30
```

This reflects the importance of infrastructure context.

For example:

```text
query.resource = "server-b-tap"
```

has higher relevance to knowledge associated with:

```text
resource = "server-b-tap"
```

than knowledge belonging to another infrastructure resource.

---

# 14. Knowledge-Type Relevance

A matching knowledge type contributes:

```text
KNOWLEDGE_TYPE_SCORE = 20
```

This allows an investigator to prioritize a specific type of knowledge.

For example:

```text
knowledge_type = RCA
```

can be explicitly requested when looking for previous root-cause analysis.

---

# 15. Source-Type Relevance

A matching source type contributes:

```text
SOURCE_TYPE_SCORE = 15
```

This allows retrieval to prioritize specific knowledge origins.

---

# 16. Tag Relevance

Matching requested tags contributes:

```text
TAG_SCORE = 15
```

Tags provide a lightweight domain signal.

Example:

```text
query tags:
    kubernetes
    memory
```

can prioritize knowledge carrying those tags.

---

# 17. Title Relevance

Title matching contributes:

```text
TITLE_SCORE = 10
```

The current implementation uses deterministic tokenization rather than an AI semantic similarity model.

For example:

```text
Query:
Kubernetes memory incident
```

can match a title containing corresponding tokens.

---

# 18. Deterministic Ordering

When candidates receive the same score, the engine uses:

```text
document_id
```

as a deterministic secondary ordering key.

The effective ordering is:

```text
score DESC
document_id ASC
```

This prevents unstable ordering between identical retrieval requests.

Determinism is important for:

* testing
* debugging
* auditability
* reproducibility
* incident investigation

---

# 19. Score Breakdown

Each `RetrievalResult` contains:

```text
score
score_breakdown
```

The score breakdown identifies the contribution of individual ranking factors.

Conceptually:

```text
score = 70

score_breakdown:
    resource       = 30
    knowledge_type = 20
    source_type    = 0
    tags           = 15
    title          = 5
```

This is more useful operationally than returning only a single unexplained relevance number.

---

# 20. Top-N Retrieval

The query contains a configurable:

```text
limit
```

value.

Example:

```text
limit=5
```

means that the retrieval engine returns at most five ranked results.

This establishes controlled context sizing before future RAG context assembly.

It also prevents uncontrolled retrieval of the entire knowledge base.

---

# 21. RetrievalResult

The retrieval result preserves both relevance information and traceability.

The result contains:

```text
document_id
title
score
score_breakdown
knowledge_type
source_type
resource
tags
source
provenance_reference
provenance_version
provenance_checksum
provenance_collected_at
provenance_collector
```

This is important because the future AI context should not contain only:

```text
"Here is some text."
```

Instead, retrieved knowledge should remain traceable to its origin.

---

# 22. Provenance Preservation

B19.8 carries forward the provenance established in B19.7.

For each result, the system can preserve:

```text
source
provenance_reference
provenance_version
provenance_checksum
provenance_collected_at
provenance_collector
```

The retrieval engine does not alter provenance.

It exposes provenance alongside retrieved knowledge.

This supports future AI-SRE investigation traceability:

```text
AI reasoning
     │
     ▼
Retrieved knowledge
     │
     ▼
Provenance
     │
     ▼
Original knowledge source
```

---

# 23. Provenance Is Not Relevance

A critical architectural distinction is maintained.

The retrieval engine does not increase relevance simply because provenance exists.

This prevents the system from confusing:

```text
"Where did this come from?"
```

with:

```text
"How relevant is this to the current question?"
```

The two concepts remain independent.

Therefore:

> **Provenance establishes traceability; ranking establishes retrieval priority.**

---

# 24. Negative Retrieval Behavior

B19.8 explicitly supports no-match behavior.

If no indexed knowledge satisfies the requested filters:

```text
results == []
```

The engine does not invent knowledge.

It does not ask an AI model to fabricate a result.

It simply reports that the retrieval operation found no matching knowledge.

This is important for trustworthy RAG.

---

# 25. Unknown Incident Handling

For example:

```text
incident_id="INC-DOES-NOT-EXIST"
```

returns:

```text
[]
```

This establishes deterministic behavior when an incident has no indexed knowledge.

The system does not fall back to unrelated incidents merely to produce an answer.

# 27. Evidence vs Knowledge vs Reasoning

B19.8 reinforces the following architectural separation:

```text
OBSERVED EVIDENCE
    │
    │ What happened?
    ▼
EVIDENCE / INCIDENT DATA

RETRIEVED KNOWLEDGE
    │
    │ What is already known?
    ▼
RAG KNOWLEDGE

AI REASONING
    │
    │ What does the combined evidence mean?
    ▼
INVESTIGATION / RCA
```

These are separate layers.

B19.8 only implements the middle retrieval layer.

# 28. TAP Governance Boundary

B19.8 has no execution authority.

The retrieval engine cannot:

* authorize a remediation
* execute Ansible
* modify Kubernetes
* modify Terraform
* restart services
* change firewall rules
* change infrastructure
* approve AI recommendations

The architecture remains:

```text
RAG Retrieval
      │
      ▼
AI Investigation
      │
      ▼
Recommendation
      │
      ▼
TAP Policy
      │
      ▼
Authorization
      │
      ▼
Job Broker
      │
      ▼
Governed Execution
```

Retrieval is therefore part of the **knowledge layer**, not the authority layer.

# 38. Architectural Significance

B19.8 is an important transition in the Server B AI-SRE architecture.

Before B19.8, the platform established:

```text
What knowledge exists?
Where did it come from?
How was it indexed?
Can its integrity be verified?
```

B19.8 adds:

```text
Which knowledge should be retrieved for this investigation?
```

This establishes the bridge between the knowledge layer and the future AI investigation layer.

The resulting AI-SRE information flow becomes:

```text
MONITOR
   ↓
DETECT
   ↓
OBSERVE

   ↓
RETRIEVE KNOWLEDGE

AI INVESTIGATION
   ↓
RCA / RECOMMENDATION
   ↓
TAP DECISION
   ↓
AUTHORIZATION
   ↓
GOVERNED EXECUTION
   ↓
VERIFICATION
   ↓
REPORTING
```

> **Monitoring detects. Observability exposes system behavior. Evidence establishes what happened. RAG supplies relevant knowledge. AI investigates and reasons. TAP governs decisions and authority. Automation executes. Verification proves the result.**
