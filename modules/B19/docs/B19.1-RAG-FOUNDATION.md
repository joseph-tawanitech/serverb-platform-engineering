# B19.1 — RAG Foundation

---

## 1. Overview

B19.1 establishes the foundational knowledge layer for the Server B AI-SRE platform.

The purpose of B19 is to provide a controlled and traceable information layer that can later support Retrieval-Augmented Generation (RAG).

B19.1 does not yet implement embeddings, vector databases, semantic search, AI reasoning, or infrastructure execution.

Instead, this stage establishes the foundational data structures, validation rules, provenance model, and deterministic repository required for later RAG development.

The foundation is intentionally provider-neutral and separated from AI model execution and TAP authority.

---

## 2. Objective

The objectives of B19.1 are:

* Define a controlled knowledge document model.
* Define knowledge classifications.
* Define knowledge source classifications.
* Validate knowledge before repository storage.
* Preserve source and provenance information.
* Support relationships between knowledge, incidents, resources, and evidence.
* Provide a deterministic repository abstraction.
* Establish the boundary between knowledge retrieval and infrastructure authority.
* Prepare the platform for future indexing and retrieval.
* Preserve tenant isolation and traceability requirements for future customer deployments.

B19.1 therefore establishes the information foundation before adding more advanced RAG capabilities.

## 4. KnowledgeDocument

The `KnowledgeDocument` is the foundational B19 knowledge object.

It represents a controlled piece of information that may later be indexed and retrieved by the RAG system.

The model contains:

* `document_id` — unique document identifier.
* `title` — human-readable document title.
* `knowledge_type` — classification of the knowledge.
* `source_type` — classification of the originating source.
* `content` — knowledge content.
* `source` — originating source reference.
* `created_at` — creation timestamp.
* `updated_at` — optional update timestamp.
* `version` — optional version information.
* `resource` — optional affected or associated resource.
* `incident_id` — optional incident relationship.
* `evidence_ids` — references to supporting evidence.
* `tags` — searchable classifications.
* `metadata` — additional structured metadata.

The model is provider-neutral.

It does not depend on:

* Ollama
* Qwen
* Claude
* GPT
* a particular embedding model
* a particular vector database
* a particular cloud provider

The knowledge model is therefore independent from the AI model layer.

## 5. Knowledge Types

B19.1 defines the following knowledge classifications:

* `documentation`
* `incident`
* `rca`
* `evidence`
* `configuration`
* `procedure`
* `architecture`
* `runbook`
* `other`

These classifications describe what type of information a document represents.

For example:

An infrastructure document may be classified as `documentation`.

A historical incident may be classified as `incident`.

A root-cause analysis may be classified as `rca`.

A validated operational observation may be classified as `evidence`.

A recovery procedure may be classified as `procedure` or `runbook`.

A network or Kubernetes design document may be classified as `architecture`.

The classification itself does not grant authority to execute an action.

## 7. Validation

B19.1 validates knowledge before it is stored in the repository.

Validation includes:

* `document_id` must not be empty.
* `title` must not be empty.
* `knowledge_type` must be a valid `KnowledgeType`.
* `source_type` must be a valid `KnowledgeSourceType`.
* `content` must not be empty.
* `source` must not be empty.
* `updated_at` must not be earlier than `created_at`.
* `version`, when provided, must not be empty.
* `resource`, when provided, must not be empty.
* `incident_id`, when provided, must not be empty.
* `evidence_ids` must be unique.
* `tags` must be unique.

Validation provides a data-integrity boundary.

Validation is not the same as:

* AI safety
* policy authorization
* execution authorization
* infrastructure verification

Those controls belong to later TAP layers.

## 8. Knowledge Provenance

B19.1 defines `KnowledgeProvenance` as a traceability record describing where knowledge originated and how it was collected.

The provenance model contains:

* `source`
* `source_type`
* `collected_at`
* `collector`
* `version`
* `checksum`
* `reference`

Provenance allows future retrieval systems to identify the origin of information.

For example, a knowledge record may reference:

```text
source: docs/B18.8-ROOT-CAUSE-ANALYSIS.md
source_type: file
collector: server-b-tap-b19
version: 1.0
checksum: sha256:example
reference: B18.8
```

Provenance is informational metadata.

It does not grant authority to execute infrastructure actions.

Operational environments change over time.

Examples include:

* network configuration changes
* application releases
* monitoring configuration changes
* infrastructure architecture changes
* runbook updates
* historical incidents
* previous RCA findings
* previous remediation results

B19.1 supports optional version metadata through the `version` field.

However, B19.1 does not yet implement:

* configuration diffing
* temporal indexing
* historical state reconstruction
* automatic change correlation
* semantic version comparison

These capabilities can be introduced in later B19 stages.

The objective is to ensure that historical knowledge can eventually be represented without confusing an old state with the current operational state.

## 11. Knowledge Repository

B19.1 provides a deterministic in-memory `KnowledgeRepository`.

The repository supports:

* `add()`
* `get()`
* `list_documents()`
* `count()`
* `remove()`
* `clear()`

Documents are validated before insertion.

Duplicate document identifiers are rejected.

Invalid documents are rejected.

Missing documents produce controlled errors.

The repository is intentionally simple at this stage.

It does not yet provide:

* persistent storage
* embeddings
* vector search
* semantic search
* ranking
* retrieval augmentation
* AI reasoning

The repository establishes a clean abstraction that can later be replaced or extended with persistent and indexed storage.

RAG means Retrieval-Augmented Generation.

RAG is an architecture or pattern rather than a specific AI model.

The intended future B19 flow is:

```text
Knowledge Sources
      │
      ▼
Collection / Ingestion
      │
      ▼
B19 Knowledge Layer
      │
      ▼
Indexing
      │
      ▼
Retrieval
      │
      ▼
Relevant Context
      │
      ▼
B17 Prompt / Context
      │

      │
      ▼

```

RAG does not inherently:

* observe infrastructure
* diagnose infrastructure
* change infrastructure
* authorize actions
* execute remediation

Instead, RAG provides relevant information to an AI reasoning process.

Future RAG retrieval may combine:

* current evidence
* historical incidents
* previous RCA records
* infrastructure documentation
* configuration history
* architecture information
* runbooks
* procedures
* operational knowledge

Retrieved knowledge is context, not automatically truth.

Future retrieval should consider:

* source
* provenance
* freshness
* version
* evidence quality
* relevance
* tenant
* access permissions

```text

      │
      ▼

      │
```

Therefore, increasing the intelligence or retrieval capability of B19 does not remove the governance boundary around infrastructure actions.

## 14. Security and Traceability Principles

B19.1 follows the principle that knowledge must be controlled, traceable, and separated from execution authority.

Key principles are:

* **Source traceability** — knowledge records identify their originating source.
* **Provenance** — collection metadata identifies when and how knowledge was obtained.
* **Validation** — invalid knowledge is rejected before repository storage.
* **Version awareness** — optional version metadata supports future historical retrieval.
* **Evidence references** — knowledge can reference supporting B18 evidence.
* **Incident relationships** — knowledge can be associated with historical incidents and RCA records.
* **Authority separation** — knowledge does not grant permission to execute infrastructure actions.
* **Provider neutrality** — B19 knowledge models do not depend on a particular AI model or vector database.
* **Tenant isolation** — future customer deployments must prevent one customer's operational knowledge from being unintentionally exposed to another customer.
* **Least privilege** — future ingestion and retrieval interfaces should expose only the data and operations required for their defined purpose.
* **Auditability** — future retrieval and ingestion operations should preserve sufficient metadata to determine what knowledge was used and where it originated.

B19 should therefore be treated as a controlled information layer rather than an unrestricted database exposed directly to an AI model.

Future security controls will expand these principles through B20 AI Security and later governed automation stages.

## 18. Glossary

### RAG

**Retrieval-Augmented Generation.**

An architecture in which relevant external information is retrieved and supplied as context to an AI model before or during generation.

### Knowledge Document

A controlled information object containing structured metadata and content that can later be indexed and retrieved.

### Provenance

Information describing where knowledge came from, when it was collected, how it was collected, and optionally its version or checksum.

### Source

The originating location or system from which knowledge was obtained.

### Version

Information identifying a particular state or revision of knowledge.

### Evidence

An observable or recorded piece of information supporting an operational investigation or conclusion.

### Incident

A recorded operational event involving an observed problem, disruption, degradation, or abnormal condition.

### RCA

**Root Cause Analysis.**

A structured investigation intended to identify the underlying cause of an incident rather than only recording its symptoms.

### Retrieval

The process of finding relevant knowledge from an indexed or stored knowledge system.

### Indexing

The process of preparing knowledge so that relevant information can be efficiently located.

### Embedding

A numerical representation of information used by some retrieval systems to compare semantic similarity.

### Vector Store

A storage system designed to store and retrieve vector representations.

### Semantic Search

Search based on meaning or similarity rather than only exact keyword matching.

### Context

Information supplied to an AI model to help it perform a task.

### Tenant

A customer or logically isolated organization within a shared platform.

### Tenant Isolation

Controls that prevent one customer's data or knowledge from being unintentionally accessed by another customer.

### Authority

The permission to perform an operational action.

B19 knowledge does not provide operational authority.

### Governance

The controls that determine whether an AI-proposed action may be authorized and executed.

### Job Broker

The TAP control boundary through which governed jobs can be authorized and dispatched for execution.

### Recorder

The TAP history and audit layer responsible for preserving operational records, execution information, and reporting data.
