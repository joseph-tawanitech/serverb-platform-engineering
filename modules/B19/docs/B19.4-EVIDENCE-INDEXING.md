# B19.4 — Evidence Indexing

## 1. Overview

B19.4 establishes the deterministic evidence indexing layer for the
Tawanitech Automation Platform (TAP) RAG architecture.

B19.3 established controlled knowledge ingestion.

B19.4 builds the next layer:

    Source
      |
      v
    Ingestion
      |
      v
    Validated Knowledge
      |
      v
    Evidence Index
      |
      v
    Future Retrieval

The purpose of indexing is to organize knowledge metadata and
traceability references so that information can be located efficiently
by future retrieval components.

B19.4 does not yet implement semantic retrieval, embeddings, vector
storage, AI reasoning, authorization, or infrastructure execution.

---

## 2. Objective

The objective of B19.4 is to create a deterministic index for
successfully ingested knowledge.

The index provides structured references to:

- Document identity
- Document title
- Knowledge type
- Source type
- Resource
- Tags
- Source
- Provenance reference

The index is therefore a navigation layer over the B19 knowledge
collection.

---

## 3. What Is Indexing?

Indexing means organizing information about stored knowledge so that
the knowledge can be found later.

A useful analogy is a library.

The books contain the actual information.

The catalog contains information that helps locate the books.

Similarly:

    Knowledge Content
          |
          v
    Metadata / References
          |
          v
    Index
          |
          v
    Retrieval

The index does not replace the original knowledge.

It provides an organized reference to it.

---

## 4. Content, Metadata, Provenance, and Relationships

B19 distinguishes several concepts.

### Content

Content is the actual information contained in a knowledge document.

Example:

    "API requests started returning HTTP 503."

### Metadata

Metadata is information describing the knowledge document.

Examples include:

- Document ID
- Title
- Type
- Resource
- Version
- Tags
- Source
- Creation time

### Provenance

Provenance records where information came from and provides traceability.

Examples include:

- Source
- Collection time
- Collector
- Version
- Checksum
- Reference

### Relationships

Relationships describe how knowledge or infrastructure objects connect.

Examples include:

    Application
        |
        +-- depends on --> Database

    Kubernetes Service
        |
        +-- routes to --> Pod

    Incident
        |
        +-- affects --> Application

Relationships are not automatically the same thing as metadata, although
relationship information may be represented as structured metadata.

## 6. EvidenceIndexEntry

B19.4 introduces the `EvidenceIndexEntry` data structure.

An index entry contains:

- `document_id`
- `title`
- `knowledge_type`
- `source_type`
- `resource`
- `tags`
- `source`
- `provenance_reference`

Conceptually:

    EvidenceIndexEntry
    |
    +-- document_id
    +-- title
    +-- knowledge_type
    +-- source_type
    +-- resource
    +-- tags
    +-- source
    +-- provenance_reference

This creates a deterministic representation of the information required
to locate and classify the corresponding knowledge.

---

## 7. EvidenceIndex

The `EvidenceIndex` class provides the B19.4 indexing boundary.

It currently supports:

- Indexing validated knowledge
- Retrieving an entry by document ID
- Removing an entry
- Listing indexed entries
- Counting entries
- Clearing the index

The implementation uses an in-memory dictionary.

The document ID is the index key.

Conceptually:

    document_id
          |
          v
    EvidenceIndexEntry

This provides deterministic metadata-based indexing without introducing
an external database or vector engine.

---

## 8. Indexing Flow

The B19.4 indexing process is:

    IngestedKnowledge
          |
          v
    Type validation
          |
          v
    Extract document metadata
          |
          v
    Extract provenance references
          |
          v
    Create EvidenceIndexEntry
          |
          v
    Store by document ID

Only successfully ingested knowledge is accepted by the index.

This preserves the boundary established by B19.3.

---

## 9. Input Validation

`EvidenceIndex.index()` requires an `IngestedKnowledge` object.

Invalid input is rejected.

For example:

    EvidenceIndex.index("invalid")

raises a `TypeError`.

This prevents arbitrary objects from entering the evidence index.

The index therefore expects the upstream ingestion layer to have already
validated the document and provenance.

## 10. Relationship With B19.3

B19.3 and B19.4 have separate responsibilities.

### B19.3 — Knowledge Ingestion

Responsible for:

    Validate
       |
       v
    Accept KnowledgeDocument
       +
    KnowledgeProvenance
       |
       v
    IngestedKnowledge

### B19.4 — Evidence Indexing

Responsible for:

    IngestedKnowledge
       |
       v
    Extract metadata
       |
       v
    Create index entry
       |
       v
    Store searchable reference

This separation keeps ingestion and indexing independently testable.

---

## 11. Relationship With Retrieval

Indexing is not the same as retrieval.

The distinction is:

### Ingestion

    Put valid knowledge into the knowledge layer.

### Indexing

    Organize references to that knowledge.

### Retrieval

    Find knowledge relevant to a request.

### Semantic Retrieval

    Find knowledge based on meaning or similarity.

B19.4 implements indexing.

B19.6 will eventually address the retrieval engine.

---

## 12. Metadata-Based Indexing

The current index is metadata-oriented.

For example, an indexed incident may contain:

    document_id:
        DOC-001

    title:
        Kubernetes API Failure Investigation

    knowledge_type:
        incident

    source_type:
        incident_record

    resource:
        server-b-tap

    tags:
        kubernetes
        api
        failure

    source:
        incident-system/INC-001

    provenance_reference:
        INC-001

This information can later support deterministic filtering and retrieval.

---

## 13. Example

Suppose B19 ingests:

    DOC-001

with content:

    "API requests started returning HTTP 503."

Its index entry may contain:

    DOC-001
      |
      +-- type: incident
      +-- resource: server-b-tap
      +-- tags: kubernetes, api, 503
      +-- source: incident-system/INC-001
      +-- provenance: INC-001

The actual incident content remains in the knowledge document.

The index provides the organized reference needed to locate it.

## 14. Why Indexing Matters for RAG

A RAG system may eventually contain large amounts of knowledge:

- Current infrastructure evidence
- Historical incidents
- RCA records
- Runbooks
- Architecture
- Configuration
- Change history
- Security information
- Application information
- Cloud information
- Kubernetes information
- Operational documentation

Searching all content blindly would be inefficient.

An index provides an organized structure that later retrieval mechanisms
can use.

The future architecture can therefore become:

    Large Knowledge Collection
             |
             v
        Index / Metadata
             |
             v
       Retrieval Filtering
             |
             v
       Semantic Retrieval
             |
             v
       Relevant Knowledge
             |
             v
          AI Context

---

## 15. Relationship With Embeddings

B19.4 does not implement embeddings.

Embeddings are expected in B19.5.

The intended progression is:

    B19.3
    Ingestion
       |
       v
    B19.4
    Evidence Index
       |
       v
    B19.5
    Embeddings / Vector Storage
       |
       v
    B19.6
    Retrieval Engine

The metadata index and future vector representation serve different
purposes.

Metadata helps identify and filter information.

Embeddings can later represent semantic meaning.

Both can eventually participate in the same retrieval architecture.

---

## 16. Provenance Traceability

B19.4 preserves the provenance reference from the ingested knowledge.

This is important because an index should not lose the ability to trace
knowledge back to its source.

The intended chain is:

    Source
      |
      v
    Provenance
      |
      v
    KnowledgeDocument
      |
      v
    EvidenceIndexEntry
      |
      v
    Retrieval
      |
      v
    AI Context

The index therefore remains connected to the original source.

---

## 17. Duplicate Document IDs

The current deterministic index uses `document_id` as its key.

Indexing another document using the same document ID replaces the
previous entry.

This behavior is intentional for the current foundation.

Future B19 modules may introduce:

- Version-aware indexing
- Duplicate detection
- Immutable historical entries
- Source version tracking
- Checksum comparison
- Update timestamps
- Knowledge lifecycle management

Those capabilities are outside B19.4.

---

## 18. Persistence Boundary

The current evidence index is in-memory.

Therefore:

- Data exists only during process lifetime.
- Restarting the process removes the index.
- No external database is required.
- No vector database is required.

This is intentional.

B19.4 establishes the indexing model before introducing persistence
technology.

Future implementations may use:

- PostgreSQL
- SQLite
- Search indexes
- Vector databases
- Object storage
- Other controlled persistence layers

The persistence technology must remain below the B19/TAP architectural
boundary.

---

## 19. Security Boundary

The evidence index does not grant infrastructure authority.

It cannot:

- Execute commands
- Modify Kubernetes
- Run Ansible
- Apply Terraform
- Change firewall rules
- Restart services
- Modify users
- Approve remediation

The index is a knowledge organization mechanism.

The TAP authority model remains:

    Retrieve
       |
       v
    AI Reasoning
       |
       v
    Decision
       |
       v
    TAP Policy
       |
       v
    Authorization
       |
       v
    Job Broker
       |
       v
    Execution
       |
       v
    Verification
       |
       v
    Recorder

---

## 20. Tenant Isolation

Future persistent and searchable indexes must enforce tenant isolation.

For example:

    Tenant A
      |
      +-- Index
      +-- Knowledge
      +-- Incidents
      +-- RCA
      +-- Runbooks

    Tenant B
      |
      +-- Index
      +-- Knowledge
      +-- Incidents
      +-- RCA
      +-- Runbooks

An index must not automatically expose one customer's knowledge to
another customer.

Tenant-aware retrieval and authorization will be addressed in later B19
security and retrieval work.

## 24. Framework Neutrality

B19.4 does not depend on LangChain, LlamaIndex, or another RAG
framework.

The index is implemented using native Python data structures.

Frameworks may be considered later when a concrete requirement exists
for advanced retrieval or orchestration.

Any future framework remains below the TAP governance architecture.

A framework must never become the infrastructure authority boundary.

## 29. Glossary

### Index

An organized structure containing references that make stored
information easier to locate.

### Index Entry

A structured record representing the searchable or identifying metadata
associated with a knowledge document.

### Metadata

Information describing a knowledge item rather than the item's primary
content.

### Content

The actual information contained within a knowledge document.

### Provenance

Information describing the origin and collection history of knowledge.

### Retrieval

The process of finding knowledge relevant to a request or investigation.

### Semantic Retrieval

Retrieval based on meaning or similarity rather than only exact
metadata matching.

### Embedding

A numerical representation of information that can be used for
similarity-based search.

### Vector Storage

A storage mechanism for embeddings and related vector search operations.

### Relationship

A structured connection between two knowledge or infrastructure
objects.

### Tenant Isolation

The separation of knowledge belonging to different customers or
organizational boundaries.

## 30. Final Principle

B19.4 establishes a simple but important architectural principle:

> **Store the knowledge separately; index the information needed to find
> it.**

The index does not replace the knowledge.

It provides the organized path to that knowledge.

The B19 progression is therefore:

    B19.3
    INGEST
       |
       v
    B19.4
    INDEX
       |
       v
    B19.5
    EMBED
       |
       v
    B19.6
    RETRIEVE
       |
       v
    B19.7
    ATTRIBUTE
       |
       v
    B19.8+
    CORRELATE + GROUND + INTEGRATE
       |
       v
    AI REASONING
       |
       v
    TAP GOVERNANCE

This preserves the separation between knowledge management, retrieval,
AI reasoning, and infrastructure authority.
