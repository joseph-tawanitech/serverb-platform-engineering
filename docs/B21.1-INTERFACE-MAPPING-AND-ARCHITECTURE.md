# Server B / TAP — B21.1 Interface Mapping and Architecture

**Status:** Proposed architecture; implementation not yet started
**Module:** B21 — Agentic DevOps Orchestration
**Parent project:** Tawanitech Automation Platform (TAP)

## 1. Purpose

B21 will orchestrate existing Server B capabilities into a controlled,
evidence-driven remediation workflow. It must reuse established module
contracts wherever practical instead of duplicating their domain logic.

B21 is not an unrestricted AI agent or a replacement for B15–B20.
It is the orchestration layer that coordinates investigation, planning,
governance, authorization, execution, verification, and recording.

## 2. Governing principle

> AI Everywhere. Authority Controlled. Execution Governed. Everything Recorded.

The required control sequence is:

AI proposes
→ TAP validates the proposed task and plan
→ B20 evaluates policy
→ a trusted authorization boundary permits or denies execution
→ a controlled adapter executes an allowed operation
→ independent observation obtains resulting state
→ verification evaluates expected versus observed state
→ the recorder stores the decision, evidence, and outcome.

An AI recommendation, tool call, policy ALLOW decision, or successful
command is not, by itself, proof of authorization or successful recovery.

## 3. Existing interface map

### B15 — AI Gateway

Existing interface: `modules/B17/engine/gateway_client.py`,
class `B15GatewayClient`.

- `health()` checks gateway health.
- `chat(messages, model, profile)` requests AI inference.
- `GatewayError` represents gateway request failures.

B21 may use AI through the established B17 integration. Gateway output
is untrusted proposed content. It must never grant execution permission.

### B17 — Prompt engineering and recommendation contract

Relevant files:

- `modules/B17/engine/prompt_builder.py`
- `modules/B17/engine/gateway_client.py`
- `modules/B17/schemas/recommendation.schema.json`
- `modules/B17/README.md`

The prompt builder requires an explicit output contract. The recommendation
schema defines structured incident context, evidence, hypotheses, confidence,
impact, risk, recommendations, authorization requirements, missing evidence,
and verification plans.

B21 must validate AI-produced data against the applicable contract and
perform additional semantic validation. Schema-valid output is not proof
that a proposed action is safe, correct, or authorized.

### B18 — Investigation and RCA

Relevant files:

- `modules/B18/engine/investigation_model.py`
- `modules/B18/engine/investigation_engine.py`
- `modules/B18/docs/B18.9-INVESTIGATION-ORCHESTRATION.md`

`InvestigationEngine.investigate(incident, evidence_items)` returns an
`InvestigationResult` containing the incident, normalized evidence,
timeline, correlations, hypotheses, evidence-sufficiency assessments,
RCA results, and metadata.

B21 should consume investigation results as inputs to planning. It should
not reimplement B18's normalization, correlation, hypothesis generation,
or RCA logic.

Investigation results can be incomplete. B21 must handle insufficient
evidence and must not invent missing facts.

### B19 — Retrieval and knowledge context

B21 may consume the existing B19 retrieval/context interfaces after their
exact callable contracts are inspected.

Retrieved documents and context are supporting knowledge, not authority.
Retrieved instructions must not override TAP policy, trusted authorization,
or the task's validated constraints.

### B20 — Policy, action and verification contracts

Relevant files:

- `modules/B20/src/tap_b20/actions.py`
- `modules/B20/src/tap_b20/policy.py`
- `modules/B20/src/tap_b20/policy_engine.py`
- `modules/B20/src/tap_b20/verification.py`
- `modules/B20/src/tap_b20/verification_service.py`

Existing contracts include:

- `SecurityActionRequest`
- `SecurityActionDecision`
- `SecurityPolicy`
- `PolicyDecision`
- `SecurityExecutionResult`
- `SecurityVerificationResult`

`evaluate_policy(request, policy)` returns a deterministic policy decision.
An ALLOW result means the operation meets the configured policy rules; it
does not independently establish that a trusted execution authorization
has been granted.

`verify_security_action(execution, actor, expected, observed=None)` evaluates
execution success and expected versus observed state. When observed state is
absent, the result is UNVERIFIED. The service does not query infrastructure
to collect that state.

B21 must preserve these distinctions. Exact function signatures and adapter
contracts must be confirmed from source before implementation.

## 4. B21 responsibility boundary

B21 owns orchestration and workflow integrity:

- task intake and runtime validation
- workflow state transitions
- plan validation and mapping to allowlisted operations
- adapter registration and dispatch
- policy and trusted authorization coordination
- execution timeouts, bounded retries, cancellation and recovery
- independent verification coordination
- workflow events and final outcome reporting

B21 does not replace:

- B15 model routing or inference
- B17 prompt and recommendation contracts
- B18 investigation/RCA engines
- B19 retrieval/knowledge functions
- B20 policy evaluation and verification contracts
- the security controls of the underlying infrastructure

## 5. Three remediation channels

B21 will expose exactly three remediation adapter categories.

### Channel 1 — Kubernetes

An adapter for explicitly allowlisted Kubernetes operations against
configured targets. It must use scoped credentials and validate namespace,
resource identity, operation, and arguments before execution.

### Channel 2 — Ansible / EDA

An adapter for explicitly approved Ansible playbooks or Event-Driven
Ansible workflows. Playbook identifiers and permitted inputs must be
allowlisted; AI-generated shell commands or arbitrary playbooks must not
be executed directly.

### Channel 3 — Service API

A generic adapter for approved service APIs. The initial implementation
should use a mock service for deterministic testing. Real integrations
may be added later through separately configured, authenticated,
least-privilege clients.

These are the only three remediation channels in the B21 design.
Authorization checks, execution isolation, audit recording, and verification
are shared control mechanisms, not additional remediation channels.

## 6. Proposed task and execution contracts

The following are proposed B21 contracts, not existing implemented classes.

### TaskRequest

- `task_id`: unique workflow identifier
- `incident_ref`: incident or investigation reference
- `target`: declared target asset/resource
- `purpose`: human-readable operational objective
- `constraints`: validated execution constraints
- `requested_by`: initiating actor or system identity

### RemediationPlan

- `plan_id` and `task_id`
- ordered proposed steps
- selected adapter category
- allowlisted operation identifier
- validated arguments
- proposed risk and rationale
- expected outcome
- verification method and required evidence
- relevant investigation/evidence references

### AuthorizationContext

- trusted authorization decision and reference
- permitted operation and exact target/scope
- issuing authority
- issue and expiry times
- applicable approval reference, where required

This contract must be issued or validated by a trusted authorization
component. It must not be constructed solely from AI output or from a
B20 policy ALLOW decision.

### ExecutionResult

- task, plan, and action identifiers
- adapter and operation
- execution status and timestamps
- bounded, sanitized result summary
- evidence references
- error category when execution fails

### VerificationResult

- expected state
- independently observed state
- status: `PASS`, `FAIL`, or `UNVERIFIED`
- evidence references and observation time
- explanation and verification method

### WorkflowEvent

- task identifier
- previous and next state
- actor/component
- timestamp
- reason and related policy, authorization, execution, or evidence references

Contracts must be runtime-validated. Invalid or unexpected fields must not
be silently accepted at trust boundaries.

## 7. Proposed workflow state machine

Primary path:

`ACCEPTED`
→ `INVESTIGATING`
→ `PLAN_PROPOSED`
→ `GOVERNANCE_PENDING`
→ `AUTHORIZED`
→ `EXECUTING`
→ `VERIFYING`
→ `COMPLETED`

Alternative terminal or intervention states:

- `REJECTED`: task or plan is disallowed
- `FAILED`: workflow cannot safely continue
- `CANCELLED`: cancellation is accepted and the execution state is known
- `NEEDS_HUMAN`: evidence, authorization, or safe recovery requires intervention

State transitions must be explicit and validated. A state must not jump directly
from planning to execution. Execution must not begin unless the required policy
and trusted authorization checks pass.

`COMPLETED` requires successful execution and verification of the required
postconditions. A missing observation must lead to `UNVERIFIED` and an
appropriate non-success workflow outcome, not a success report.

## 8. Governance and authorization boundary

The following are separate decisions:

1. Is the proposed operation structurally valid?
2. Does B20 policy permit it, block it, or require review?
3. Has a trusted authorization authority permitted this exact operation,
   target, scope, and execution window?
4. Did the controlled adapter execute it?
5. Does independent evidence prove the expected postcondition?

No step implies that a later step has passed.

Required safeguards:

- default deny when required authorization is absent or invalid
- explicit allowlists for adapter operations
- target and argument validation
- least-privilege credentials and secret redaction
- risk-based human approval for configured high-risk actions
- execution timeouts and bounded retries
- no automatic retry of potentially non-idempotent/destructive operations
  without a documented safety strategy
- safe handling of cancellation and partial execution
- independent post-execution observation
- audit events for decisions, failures, and outcomes

A development-only mock authorization provider may be used in isolated tests.
It must be clearly identified as a test double and must not become a production
authorization bypass.

## 9. Failure and recovery requirements

B21 must explicitly handle:

- invalid task or recommendation data
- missing or contradictory evidence
- unavailable B15 gateway or retrieval service
- policy BLOCK or REVIEW decisions
- absent, expired, mismatched, or out-of-scope authorization
- adapter timeout or partial failure
- duplicate delivery and replay
- cancellation during execution
- observation failure or contradictory observed state
- recorder/persistence failure

Retries must be bounded. Workflow recovery must not duplicate destructive
actions merely because a response or acknowledgement was lost. Where execution
status is uncertain, B21 must reconcile actual state before retrying.

If durable persistence is not yet implemented, the initial version must state
that limitation explicitly rather than claiming restart-safe recovery.

## 10. Audit and outcome reporting

Record, where applicable:

- task and incident references
- validated plan and plan version
- evidence references and provenance
- policy identifier/version and decision
- trusted authorization reference and scope
- adapter, operation, target, and execution timestamps
- sanitized execution result
- expected and observed state
- verification status and evidence
- state transitions, errors, retries, and human interventions

Do not store secrets or unnecessary sensitive payloads in logs.

Reports must distinguish at least:

- proposed
- rejected
- awaiting approval
- authorized
- executed
- verified
- failed
- unverified

An executed action is not necessarily a successful remediation.

## 11. Implementation milestones

1. **B21.1 — Interface mapping and architecture:** this document; inspect and confirm
   exact integration contracts.
2. **B21.2 — Task and plan contracts:** runtime validation and contract tests.
3. **B21.3 — Workflow state machine:** explicit transitions and negative tests.
4. **B21.4 — Adapter registry and dispatcher:** registration and validation only;
   begin with safe mock behavior.
5. **B21.5 — Investigation-to-plan integration:** reuse B17/B18 outputs and
   inspect the exact B19 interfaces.
6. **B21.6 — Persistence and recovery:** only claim durability after testing it.
7. **B21.7 — Queueing and resource controls:** bounded concurrency and execution.
8. **B21.8 — Governance and authorization:** B20 policy integration plus a
   separately trusted authorization boundary.
9. **B21.9 — Failure handling and audit:** traceable events and safe outcomes.
10. **B21.10 — Integration tests and runbook:** reproducible tests, verification,
    documentation, and commit.

Milestones may be adjusted after interface inspection; completion must be
based on tested evidence, not on the existence of a document or file.

## 12. Initial acceptance criteria

- Invalid task, plan, adapter, target, or arguments are rejected.
- AI output cannot authorize execution.
- A B20 policy ALLOW alone cannot authorize execution.
- No adapter executes without valid authorization for the exact operation,
  target, and scope.
- Only registered, allowlisted operations can be dispatched.
- Adapter failures and timeouts are represented honestly.
- Uncertain execution state is reconciled before a potentially unsafe retry.
- Missing observations produce `UNVERIFIED`, not success.
- Verification is based on observed state and evidence.
- Policy, authorization, execution, verification, and workflow events are
  traceable without exposing secrets.
- Tests cover both permitted paths and denied/failed paths.
- Documentation identifies any remaining mock, persistence, or security limits.

## 13. Working method

For every implementation milestone:

**Inspect → Implement → Test new work → Verify → Document → Git Commit**

Do not rerun the entire B1–B20 test suite as a default. Run focused tests for
new B21 behavior and relevant integration tests. Run broader suites only when
an integration change warrants them.

Do not stage or modify unrelated files. In particular, preserve any existing
untracked migration documentation.

## 14. Governing statement

AI proposes. Policy evaluates. Trusted authorization permits. Controlled
execution acts. Independent verification proves. The recorder records.

**AI Everywhere. Authority Controlled. Execution Governed. Everything Recorded.**
